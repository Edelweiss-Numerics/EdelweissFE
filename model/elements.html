Elements

Relevant module: edelweissfe.config.elementlibrary

EdelweissFE currently supports finite element implementations provided by the Marmot library. In future, elements by other providers or elements directly implemented in EdelweissFE may be added here.

Example:
*element, type=C3D8, provider=marmot
    ** el_label, node1, node2, node3, node4, ...
    1000,        1,     2,     3,     4,     ...
edelweissfe.config.elementlibrary.getElementClass(elType, provider=None)[source]

Return the class implementing element type elType for the given provider.

provider selects a namespace, not a variant of one lookup, and is dispatched via an explicit table rather than the registry: marmot and marmotsingleqpelement ignore elType entirely and return a single wrapper class that resolves the type at the Marmot boundary.

The edelweiss provider is resolved through the registry (element category), keyed by element type, which lets a third party contribute an element type through an entry point.

Parameters:

  • elType (str) – A string identifying the requested element formulation.

  • provider (str) – The name of the element provider to load.

Returns:

The element provider class type.

Return type:

type

Raises:

edelweissfe.config.registry.RegistryLookupError – If provider is edelweiss and no element is registered under elType.

The element type definition has to be of the following form:

Elements

One of the following element types needs to be included in the definition (type in .inp file).

  • CPE4 - quadrilateral 2D element with 4 nodes and plane strain.

  • CPE8 - quadrilateral 2D element with 8 nodes and plane strain.

  • CPS4 - quadrilateral 2D element with 4 nodes and plane stress.

  • CPS8 - quadrilateral 2D element with 8 nodes and plane stress.

  • C3D8 - hexahedron 3D element with 8 nodes.

  • C3D20 - hexahedron 3D element with 20 nodes.

Note

C3D8/C3D20 (and their TL counterparts) use the standard Abaqus node ordering (corner ring 1-4 at \(\zeta=-1\), ring 5-8 at \(\zeta=+1\)), matching the marmot provider’s elements – there is only one node-ordering convention across the framework.

additional Parameters

The following optional Parameters are also included in the element type definition:

  • R - reduced integration for element, at the end of elementType.

  • E - extended integration for element, at the end of elementType.

  • N - (optional) regular integration, at the end of elementType.

  • TL - use the total Lagrangian element, before integration type.

Common base

Both elements below share everything that does not depend on the kinematics – geometry and quadrature, material and quadrature-point state, loads, mass and result access – in a common base class. Each element adds only how strain and stress follow from the nodal displacements.

Contact facet elements

Relevant module: edelweissfe.elements.contactsurfaceelement

Thin, material-less, volume-less elements (Tria3ContactFacet/Line2ContactFacet) sharing the ordinary displacement DOFs of a deformable body’s boundary nodes, used as the master side of node-to-deformable-surface contact. Not user-constructed directly – see the surfaceElementGenerator generator.

Because a facet has neither a material nor a state, its kernels, its internal energy and its state acceptance are all no-ops, and it reports hasKernels = False. The model leaves such an entity out of its discrete system (discrete system): the facet has no block in the system matrix and no location, and no solver calls into it on any increment. Its nodes have rows only through the elements that carry kernels: a node that only a facet touches is numbered but has no row, and the discrete system refuses it, naming the node. A load on an element set that holds facets, e.g. a body force on all, acts on the elements of the set that are located. An element of your own needs to do nothing here: BaseElement reports True, which is right for any element that carries a material.

Implementing your own elements

Relevant module: edelweissfe.elements.base.baseelement

An element follows the rule every entity of the discrete system follows (see The residual and the tangent): each method adds a residual contribution P and its tangent K = dP/dU. computeKernels(K, P, U, dU, time, dT) adds the internal forces and the stiffness matrix – the tangent comes first in its arguments; the load methods computeDistributedLoad and computeBodyForce add the negative of the external load, and its tangent if the load follows the deformation.

An element carrying a material should also implement updateMaterialProperty(), through which the changeMaterialProperty step action changes a material property during an analysis. Unlike setMaterial, it must keep the element’s state: neither reset nor re-initialize the state variables, and keep the arrays holding them, which field outputs keep viewing.

Implementing your own finite elements can be done easily by subclassing from the abstract base class BaseElement.

Evaluate the diagonal of the lumped damping of the element, over every field it carries.

The coefficient of each field’s FIRST time derivative: zero on the displacement block, and the non-local viscosity on a non-local block – always, whether or not that field also carries a micro-inertia.
