Restart

An analysis writes restart checkpoints with *output, type=restart (see Outputmanagers) and resumes from one with *restart, readFrom=<checkpoint> (see <no title>). This page describes the one rule restart follows, and how each part of the code keeps it.

The rule

A checkpoint is written after an increment is accepted. A resumed run continues with the next increment and performs exactly the operations the uninterrupted run performed from there.

So a resumed run ends bitwise identical to the uninterrupted one – not “close to” it. Nothing in restart uses a tolerance. The rule has three consequences, each kept by construction:

  1. Everything carried from one increment to the next is written into the checkpoint, exactly as it is, and read back. Nothing is re-derived or reconstructed. What is a pure function of the restored model needs nothing.

  2. The step start is not repeated. Step-start actions (initial conditions, material initialization, prescribed fields), the zero increment, the step-start topology update and the first contact search all happened before the checkpoint was written. Whether a step is at its start is part of the time stepper’s state (isAtStepStart()): nothing accepted yet. A restored time stepper never is, so a resumed step skips them – there is no separate “resumed” flag.

  3. The increment loop is written once, and decides by increment number. Topology checks, contact searches, output and checkpoints happen at the same increments whether a run started cold or was resumed.

A checkpoint file is written under a temporary name and renamed once complete, so a job killed while writing one never leaves a truncated checkpoint behind. Each carries a serial number, by which the restart writer finds the oldest one to replace – not by file times, which copying changes.

Whatever cannot keep the rule refuses to resume, with a RestartError: a solver that does not checkpoint its state (the default of readRestart()), and a checkpoint of another format version (every checkpoint carries one, and a run reads its own only), and a resume past a modelupdate – it executes an arbitrary expression whose effect no checkpoint records, so a run is resumed only from checkpoints written in steps before the first one.

One increment, and where the checkpoint is written

The step’s increment loop (solve()) is the same for every solver:

increment n
├── prepare      topology update when due: model modifiers   (implicit: every increment;
│                (e.g. AMR), then ties and contact catch up    explicit: at the step start and
│                                                               after every topology-check-
│                                                               frequency-th increment)
├── propose      the time stepper proposes the increment
├── attempt      Newton iterations / explicit update; if it fails: reject, retry smaller
├── accept       solver: material state, solver state (predictor, external work, ...)
│                time stepper: progress, size of the next increment
└── output       field outputs, output managers, the CHECKPOINT last
                                            ▲
a resumed run starts here ──────────────────┘  with increment n + 1

The topology update comes before the proposal, because a refinement may lower the stable time increment of an explicit analysis. An increment retried after a cutback starts from the same accepted state, so the model modifiers are not asked again: they decide once per accepted state.

Restoring a checkpoint

The model is first rebuilt from the same input file, then restored in this order:

What

How

model time

read

mesh

the mesh rebuilt from the input file is checked against the one the checkpointed run started from (setupFingerprint()), then the recorded topology decisions the model has not applied yet are replayed through the model modifiers’ own apply (replayHistory()), and the result is checked against the recorded fingerprint; the time of a replay is printed in a performance table of its own, before the resumed step’s table

ties, contact surfaces

catch up with the replayed mesh, as they had in the uninterrupted run

node fields, scalar variables, element state, additional parameters (e.g. the load parameter the arc length method publishes)

read; a node field with all its entries (see Node field results), a checkpoint lacking one is refused

rigid bodies

their surface nodes are moved to the restored configuration

constraint state (e.g. a frozen contact search)

read; adopted only if it refers to the restored model’s contact points, otherwise refused

output managers’ sequence bookkeeping

read, including each restart writer’s position in its write interval and its record of the checkpoints a step may fall back to: the one resumed from, and those before it whose files still hold them

time stepper

its state after the last accepted increment, as it is: progress, increment counter, the size of the next increment, the enforced time increment, and whether the zero increment was done

solver

its state between increments: the implicit solver’s predictor (the last accepted increments and their dU, with the digest of the numbering of the degrees of freedom these are vectors of, under arc length control also their increments of the load parameter, and the load parameter of the step) and the time average fluxes of the Abaqus convergence criterion, the implicit dynamic solver’s conservation check and whether the initial acceleration of the step is still to be computed (in a checkpoint written after the zero increment, it is: the first real increment computes it), the explicit solver’s last increment, net force, accumulated external work and the energy at the start of its step. The resumed step extrapolates the last accepted increments only if its first discrete system numbers the degrees of freedom as they are numbered (see Solvers)

Going back to a checkpoint within a run

A step that may fall back to a checkpoint (maxCheckpointFallbacks, see Steps) restores one within the running job, by the same pieces and in the same order as a resumed run: the model, the time stepper, then the solver begins the step anew – a restored time stepper is not at the step start, so nothing of the step start is repeated – and takes over the checkpointed state together with the step actions, output managers and field outputs (fallBackToCheckpoint()). The model has not been rebuilt then, so of the recorded topology decisions only those it has not applied yet are replayed – none, since it can go back only to a checkpoint of its own mesh: a mesh change cannot be undone, and a model whose mesh has changed since the checkpoint refuses it, before anything is restored (MeshChangedSinceCheckpoint). The checkpoints are those of the one restart output of the job; a step that may fall back refuses to start with none or several.

Adding something that carries state between increments

Declare it. Every solver, convergence criterion, time stepper, constraint and output manager states which of its attributes it carries from one increment to the next, by name and type, and the checkpoint writes and reads exactly those, as they are (checkpointedstate):

The declaration of the implicit solver, NIST
checkpointedState = {
    "prevTimeStep": TimeStep,
    "dUOfLastIncrement": np.ndarray,
    "timeStepOfIncrementBeforeLast": TimeStep,
    "dUOfIncrementBeforeLast": np.ndarray,
    "dofNumberingOfLastIncrement": str,
    "convergenceCriterion": ConvergenceCriterionBase,
}

A component that carries nothing declares an empty mapping. One whose state is not a plain attribute (Ensight’s sequence bookkeeping, a frozen contact search) overrides getRestartData and setRestartData instead. A component that declares nothing cannot be checkpointed: tests/test_checkpointed_state_declared.py checks every class in the package, so a forgotten declaration fails there, and writing a checkpoint refuses. A solver that is not restartable says so by keeping the declaration None.

Step actions declare their state too: a load ramped over several steps accumulates from step to step, most actions switch themselves off at the end of their step, and an arc length controller derives the change of its controlled quantity over the step from the model it is declared on. A resumed run skips the steps before the checkpoint, and declares the step actions on the restored model, so it restores that state rather than re-deriving it.

Field outputs carry their history the same way, and how much of their export file belongs to the run: before its first write after a checkpoint is restored, the file is cut back to that size, so the rows an interrupted run wrote after its last checkpoint, or a step falling back to a checkpoint discards, are replaced, not duplicated.

Then add a scenario to tests/test_restart_exhaustive.py: it resumes from every checkpoint of a small run and requires the bitwise-identical end state, the same checkpoints and the same output.
