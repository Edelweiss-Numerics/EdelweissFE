System matrix assembly

Assembling a sparse system matrix from element, cell or particle contributions can be done two ways, and EdelweissFE provides both. Which one is appropriate is a memory question far more than a speed one, so this page describes what each costs as well as what each does.

Both paths are in edelweissfe.numerics.csrgeneratorv2, backed by the C++ header edelweissfe/numerics/_csrcore.h.

The block of an entity

Every element, constraint or other entity that couples nodes contributes a block to the system matrix, and knows it only in its own numbering: row a and column b of the block are its a-th and b-th degree of freedom (SystemMatrixContributorBase). Where these lie in the global system is its global DOF list, which the DofManager numbers; the DOF manager knows nothing about the system matrix.

  • By default an entity couples all its degrees of freedom: its block is the dense nDof x nDof matrix, stored column-major, as every element writes it.

  • An entity that couples only some of its degrees of freedom (a contact constraint couples each slave node with the master side, but not the slave nodes with each other) lists the local row and column of every value of its block: it overrides localEntriesOfBlock(), and its block is the list of the values of these entries (couplesAllItsDofs is then False).

The number of values of a block is nDof**2 for a dense block, and the length of the list otherwise. It cannot tell the layout: a list can have exactly nDof**2 entries, as a rigid body contact with a single slave node in 3D has (36 + 9 + 18 + 18 = 81 = 92), in an order that is not column-major. So the entity declares the layout, and an assembly never guesses it. It declares it once, by overriding the list or not: a subclass that also declares couplesAllItsDofs is refused when it is defined, since the direct path reads the flag and the VIJ path the list, and two declarations that disagree would assemble two different matrices. An extension type, which cannot inherit the base class (the Marmot elements, for one), declares a dense block itself, with the dense list.

The entity writes its tangent into the view shapeBlock() makes of the values of its block – a 2-D array for a dense block, a structured view for a list of its own.

The two paths

Stage, then gather (VIJSystemMatrixAssembly), the textbook path. Every value of every block has its own slot in one long VIJ (COO triplet) layout: the value V[k], its global row I[k] and its global column J[k]. The assembly derives I and J in one visible step, the local-to-global step: the entity’s local rows and columns looked up in its global DOF list, I = idcs[localRows], J = idcs[localColumns]. The CSR pattern is then derived from I and J by sort-and-sum (CSRGenerator), together with a gather map: for each of the nnz CSR entries, the VIJ slots that sum to it. Every entity writes its block into its own slice of V, and the gather sums the duplicates into CSR.

Scatter directly (DirectCSRSystemMatrixAssembly), the memory-efficient path, chosen with the solver option systemMatrixAssembly=direct. It derives its own CSR pattern from the entities’ DOF lists, row by row, without any I/J pair, and knows for every value of every block its destination in advance (DirectCSRAssembler). Each block is pushed straight into the CSR data array. Neither a value array nor index arrays of the VIJ layout are ever materialised. The destination of a value is kept one of two ways:

  • by row, for a dense block: the global row of each local row, and for every value offset, the position of its column within its row, so that the destination is indptr[row] + offset. The offset takes 16 bits, which reach the first 65,536 entries of a row.

  • by position, for every other block: every value keeps its destination, a 32-bit position in the CSR data. That is a listed block, whose values share no rows to factor out, and a dense block with a degree of freedom in a row longer than 16-bit offsets reach.

The entries in bold are why this matters: the more duplicate contributions land on the same matrix entry – which grows with the number of entities touching a DOF, not with the DOF count itself – the larger the VIJ arrays and gather_sources become relative to the CSR result they produce. Their size is set by the number of values of all blocks; the CSR pattern’s is set by nnz. A discretisation where many entities contribute to the same entries (a wide stencil, or overlapping supports) can have the staging arrays dwarf the actual result by a wide margin. For the dense blocks of the elements and the other entities, the direct path holds 2 bytes per value instead of 20.

In the implicit solvers

The implicit solvers assemble their tangent through one interface, SystemMatrixAssembly, so that neither the solver nor an element, constraint or load knows which path is in use. Every entity asks for its block – Ke = K[element] – and writes it; the solver then asks for the assembled matrix. The solver option systemMatrixAssembly selects the path:

*solver, solver=NISTParallel, name=theSolver
    systemMatrixAssembly=direct

vij (the default) is VIJSystemMatrixAssembly, stage then gather; direct is DirectCSRSystemMatrixAssembly, scatter directly. NIST, NISTParallel, NISTPArcLength, NID and NIDParallel support both; NEST assembles on the VIJ path only.

What the direct path has to know about the entities and the solvers:

  • Listed blocks. The block of an entity that lists its entries itself (see The block of an entity) is scattered entry by entry; a dense block row by row, unless it has a degree of freedom in a row too long for 16-bit offsets (see Two independent derivations of the pattern, tested against each other).

  • Worker threads. Each thread of the parallel element loop writes through blocks of its own (blocksOfWorker()), a scratch array, and adds every block to the one CSR matrix of the assembly with atomic additions, see One CSR array, atomic additions. The loop deals the elements out to the workers in a fixed way (mapChunksOnWorkers()), so that no two threads use the same scratch array at the same time.

  • More than one matrix. The arc length method needs the tangents of its dead load and its reference load besides the tangent of the elements. It adds them to the tangent of the increment as blocks scaled by \(1 - \lambda\) and \(\lambda\) (scaledBy()), on both paths, so that no further matrix is held. The dynamic solver holds one: the mass, assembled once through the same interface (every element writes its consistent mass into its block) and kept with values of its own on the sparsity pattern of the tangent (copyOntoSparsityPattern()), which shares the pattern arrays. Its effective tangent \(\boldsymbol{K} + \boldsymbol{M}/(\beta \Delta t^2) + \gamma \boldsymbol{C}/(\beta \Delta t)\) adds the mass and the lumped damping during the assembly, like the block of an entity (addMatrix(), addLumpedMatrix()): the direct path adds them to its CSR values at once, which hold the sum from the start of the assembly; the VIJ path adds them after its gather, which overwrites the CSR values. On the VIJ path the effective tangent is therefore the gathered tangent plus the scaled mass, which agrees with gathering the sum to round-off.

  • The complete pattern. The multi-point-constraint condensation adds entries to the CSR pattern. The solver builds the condensation first and hands its condensedPatternFillIn() to the assembly, which adds the entries to its pattern before anything is mapped to it, whenever the discrete system is (re)built. Both paths add them by the same merge.

Every block of the direct path is a zeroed scratch array, so an entity that is handed its block twice in one assembly (an element, and a body load on it) has each scattered on its own; on the VIJ path the second adds to the first in the same slice. Either way, an entity only adds to or overwrites its block, and never reads it.

Why the direct path is also faster

Three effects:

  • Nothing has to be cleared. The staging array must be zeroed every Newton iteration; that cost scales with the number of COO pairs, not with nnz. The direct path clears only the CSR data array, sized by nnz.

  • Nothing has to be re-read. The gather random-accesses the staging array, which can be many times larger than the CSR data the scatter touches instead.

  • The evaluation itself is not slower, because each entity writes into a small reused scratch block that stays in cache instead of a slab of a much larger array.

The relative sizes of these three effects depend on how many duplicate contributions land per matrix entry for a given discretisation and thread count – measure on the model at hand rather than assuming a fixed ratio.

Two independent derivations of the pattern, tested against each other

The two paths derive the CSR pattern each in their own way, from the same entities:

  • Sort-and-sum (VIJ path). Every (I[k], J[k]) pair is packed into one 64-bit key; the keys are bucketed by row, sorted, and the duplicates collapsed. The sort also yields the gather map. Its sort element is a key plus the pair’s origin index, and gather_sources and assembly_ptr index the pairs with 32-bit integers, so this path refuses more than INT32_MAX values of all blocks. For a discretisation with many duplicate contributions per matrix entry that limit can bite well before memory does.

  • Row by row (direct path). The entities’ DOF lists are transposed into, per row, the entities touching it and as which of their local rows (a counting sort). Each row is then the union of the columns these entities couple it with – all DOFs of a dense block, the columns of the listed entries in that local row otherwise –, collected with a marker array of nDof integers per thread, and sorted. A count pass sets indptr, a fill pass writes indices; the result does not depend on the number of threads. No pair is ever materialised, and no 32-bit quantity but nnz remains: the direct path is the one for models beyond the VIJ path’s limit.

The tests derive both patterns for random dense and listed entities (among them a list with exactly nDof**2 entries), with and without added entries, on one and on several threads, and require them to be identical.

The map of the direct path is built by binary-searching each value’s (row, column) in the pattern. For a dense block it stores the within-row position, which is why 2 bytes suffice for the bulk of a model: the length of most rows is set by the stencil, not by the problem size. Not every row’s is: the row of a rigid body’s reference point has an entry for every slave node it is coupled with, and the condensation of a multi-point constraint can couple a master degree of freedom with many others. Before mapping, the assembly looks at the rows of every dense block; a block with a degree of freedom in a row longer than 65,536 entries keeps the positions of its values in the CSR data instead, as every listed block does. So no row is too long for the direct path, and a model without such rows pays nothing for them. A value whose entry is not in the pattern raises rather than being silently misplaced.

One CSR array, atomic additions

All threads scatter into the one CSR data array of the matrix being assembled, and every addition to an entry is atomic (#pragma omp atomic), so threads that add to the same entry at the same time cannot lose a contribution. Nothing else is held per thread but a scratch array the size of one block.

The alternative, a private copy of the CSR data per thread summed at the end, needs no synchronisation, but it holds nThreads x nnz x 8 bytes and sums all copies once per assembly. Measured on real assemblies, it was not faster than the atomic additions, and its memory grows with the number of threads until it exceeds what the direct path saves by not staging the values. So there is one way, the atomic one:

  • The cost of an atomic addition is the instruction, not contention. Threads rarely add to the same entry at the same time, so the cost does not grow with the number of threads.

  • What the atomic additions give up is bit-reproducibility, not correctness. The order in which the threads add to an entry depends on their timing, so the same assembly repeated with more than one thread agrees with itself to round-off, not bit for bit. A Newton iteration whose convergence hinges on the last bit (e.g., a frictional contact that sticks or slips by a hair) may take a different path than the VIJ path does.

Validation

The addressing is validated exactly, without a floating-point tolerance, using an integer trick: the tests give every value of every block 1, so each CSR entry becomes the count of its contributions, then its own index k in the VIJ layout, so it becomes the sum of their indices. Both are integers far inside 253, so the matrix the direct path scatters is compared bit for bit with the one updateInPlace() gathers from the same entities. A transposition or an off-by-one shows up as an unmistakable mismatch instead of a judgement call about how large a deviation is acceptable. Sums of such integers are exact in any order, so the check stays exact with the threads adding in an order set by their timing.

Reference

The assembly of the system matrix: where every element, constraint and load writes its block of the tangent, and how the blocks become the global matrix in CSR format.

An implicit solver assembles the tangent from the blocks of all entities: Ke = K[element] hands out the array the element writes its block into, and SystemMatrixAssembly.assembledMatrix() sums all blocks into the global matrix. Two ways of summing are implemented behind this one interface, so that neither the solvers nor the entities know which is in use (see System matrix assembly):

VIJSystemMatrixAssembly

Every block has its own slice of one long value array (VIJ, or COO, layout), and the duplicates are gathered into CSR afterwards.

DirectCSRSystemMatrixAssembly

Every block is scattered into CSR right after it was computed; no value array exists.

class edelweissfe.numerics.systemmatrixassembly.DirectCSRSystemMatrixAssembly(dofManager, numberOfWorkers, patternFillIn=None)[source]

Scatter directly: every block is scattered into CSR as soon as it is committed, through a map that knows the CSR position of every value of every block (DirectCSRAssembler). The CSR pattern is derived from the entities’ DOF lists; neither a value array nor index arrays of the VIJ layout exist.

Every worker writes its blocks into a scratch array of its own, and all workers add them to the one CSR matrix, each addition atomic. The order in which the workers add to an entry depends on their timing, so with more than one worker the matrix agrees from run to run to round-off, not bit for bit.

Every block is a zeroed scratch array: an entity that is handed its block more than once in an assembly (an element, then a body load on it) has each one scattered on its own. Entities that list the entries of their block themselves (constraints that couple only some of their degrees of freedom, see localEntriesOfBlock()) are scattered entry by entry.

class edelweissfe.numerics.systemmatrixassembly.SystemMatrixAssembly(numberOfWorkers)[source]

The system matrix of an implicit solver while its entities assemble it, and the CSR matrix it becomes.

One assembly per Newton iteration: beginAssembly(), then every entity writes its block (K[entity], or from a worker thread, K.blocksOfWorker(worker)[entity]), then assembledMatrix() returns the global matrix. It is built per discrete system, together with its CSR pattern, see createSystemMatrixAssembly().

class edelweissfe.numerics.systemmatrixassembly.VIJSystemMatrixAssembly(dofManager, numberOfWorkers, patternFillIn=None)[source]

Stage, then gather: every block is the entity’s own slice of one value array in VIJ (COO) layout, which is gathered into CSR, summing the duplicates, once all blocks are written.

The textbook way: every value V[k] of a block has its global row I[k] and column J[k], the entity’s local row and column (localEntriesOfBlock()) looked up in its global DOF list, and the CSR matrix is the sum of all (I[k], J[k], V[k]).

The blocks of all workers are slices of the same array, and no two entities share a slice, so the workers need nothing of their own. An entity that is handed its block more than once in an assembly (an element, then a body load on it) adds to what is there.

Parameters:

  • dofManager (DofManager) – The DOF manager of the discrete system: the global DOF list of every entity.

  • numberOfWorkers (int) – How many threads may write blocks at the same time.

  • patternFillIn (Callable | None) – Called with the CSR pattern (as a matrix of zeros) once it is derived; returns the entries no entity contributes that the pattern must have as well (e.g. condensedPatternFillIn()).

Attributes:
csrMatrix

The CSR matrix the assembly assembles into, the one assembledMatrix() returns: its own buffer, which the next assembly overwrites, and whose pattern must not change.

class edelweissfe.numerics.csrgeneratorv2.DirectCSRAssembler

Scatters entity blocks straight into a CSR data array, with no VIJ staging array and no I/J pairs.

The alternative to CSRGenerator’s stage-then-gather. It derives its own CSR pattern from the entities, row by row (csrPatternOfEntities()), adds the entries patternFillIn asks for, and then maps every value of every block to its CSR entry. The two derivations of the pattern are independent, and tested against each other.

It assembles into the CSR data array of its own matrix, csrMatrix: all threads scatter into that one array, each addition atomic. The order in which the threads add to an entry depends on their timing, so the values agree with a serial assembly to round-off, not bit for bit.

Parameters:

  • entities – The SystemMatrixEntities table; entity e is number e in scatterBlock().

  • nDof – The number of rows and columns.

  • numThreads – Threads used for the pattern, the map and the zeroing, and how many may scatter at the same time (0 <= tid < numThreads in scatterBlock()).

  • patternFillIn – Called with the pattern (as csrMatrix, zero values) before the map is built; returns the entries to add to it (CSR, sorted rows, columns inside the matrix, none already in the pattern), assembled as stored zeros, e.g. condensedPatternFillIn().

Add one entity’s block – dense or listed, as the entity declared it – from a scratch buffer to csrMatrix.

Every addition is atomic, so any number of threads scatter at the same time, as long as no two concurrent callers pass the same tid (0 <= tid < numThreads), which selects the caller’s own row scratch. Releases the GIL, so the workers of a threaded entity loop scatter side by side; see DirectCSRSystemMatrixAssembly.

Raises IndexError for a tid or an entity out of range, and ValueError for a block that does not have the number of values of the entity’s block. (A compiled caller that scatters through corePointer is not checked.)

class edelweissfe.numerics.csrgeneratorv2.AliasedCSRMatrix(arg1, shape=None, dtype=None, copy=False, *, maxprint=None)

The csr_matrix returned by CSRGenerator.updateInPlace() and held by DirectCSRAssembler, and a copy of it with values of its own on the same pattern (copyOntoSparsityPattern()).

Its indices/indptr buffers are owned by the generator’s C++ core (and so are the data of the generator’s own matrix, which the core rewrites in place on every subsequent updateInPlace call via a gather/scatter map fixed once at construction time); a copy on the pattern shares them. Structurally mutating this matrix (eliminate_zeros(), prune(), sum_duplicates(), resize(), or reassigning .data/.indices/.indptr to arrays of a different length) would silently desynchronize that fixed map from the (now compacted/reshaped) matrix – every subsequent update would then write numerically correct values into the wrong (row, col) slots, with no error or warning. See GitHub issue #72.

This subclass turns that into a loud failure instead of silent corruption. If you need to reduce/reshape the pattern for a one-off use, copy the matrix first – .copy() (here and via CSRGenerator.updateCSR()) always returns a plain, unrestricted csr_matrix. Reassigning .data, .indices or .indptr to another array, even of the same length, is refused as well: the next update writes into the old one. The values are changed in place (matrix.data[...] = ..., matrix.data *= ...).

The guard only applies once the matrix is locked (lock()), when its construction is complete: scipy’s own csr_matrix.__init__ calls self.prune() internally as part of its format check, which must go through unhindered.

Notes

The semantics are not identical to numpy.ndarray.resize or numpy.resize. Here, the same data will be maintained at each index before and after reshape, if that index is within the new bounds. In numpy, resizing maintains contiguity of the array, moving elements around in the logical array but not within a flattened representation.

We give no guarantees about whether the underlying data attributes (arrays, etc.) will be modified in place or replaced with new objects.
