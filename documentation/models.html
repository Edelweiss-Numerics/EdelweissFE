buildEquationSystem(withSystemMatrix=True)[source]

Lay out the global equation system of the model as it is now: number its degrees of freedom, and say which elements contribute to it, see EquationSystemLayout. Called by a solver whenever it (re)builds its equation system: at the start of a step, and after the topology update reported a change of the mesh or of the coupling (updateConnectivity()).

The equation system of a finite element model holds the node fields, the elements, and the active constraints with their scalar variables (e.g. Lagrange multipliers). A constraint that is not active (see active) is left out together with its scalar variables, which would otherwise be unknowns without an equation.

Parameters:

withSystemMatrix (bool) – False for an explicit solver, which assembles no system matrix: then neither the pattern of the system matrix is built, nor the map from the degrees of freedom back to their nodes, by which the Newton iterations report the nodes with the largest residuals.

readRestart(restartFile, journal=None)[source]

Read the state of the model from a restart checkpoint written by writeRestart().

Either the model has been rebuilt from the original .inp file and prepareYourself() called – a resumed run – or it is the very model the checkpoint was written from, going back to it within the run (see fallBackToCheckpoint()). Of the recorded topology decisions, those the model has not applied yet are replayed: all of them for a rebuilt model, none for a model going back. A model whose mesh has changed since the checkpoint cannot go back to it, since a mesh change cannot be undone.

Parameters:

  • restartFile (File) – An open, readable h5py.File (or group) to read the checkpoint from.

  • journal (Journal) – Optional Journal for the progress messages of the topology replay.

Raises:

  • RestartError – If the model is not the one the checkpoint was written from, before anything is restored, or if the checkpoint does not hold every entry of a node field (see ENTRIES).

  • MeshChangedSinceCheckpoint – If the model’s mesh has changed since the checkpoint was written, before anything is restored.

updateConnectivity()[source]

Bring the coupling of the degrees of freedom up to date with the converged state, before an increment: which nodes the entities of the equation system couple. Called by the solvers’ topology update at the start of every increment and of every retry after a cutback, before the increment is proposed (see updateTopologyAndConnectivity()). If it reports a change, an implicit solver rebuilds its equation system (buildEquationSystem()).

In a finite element model, the elements keep their nodes, and only a constraint may change the nodes it couples: a contact constraint searches for the surface it touches. A meshfree model of EdelweissMeshfree moves its material points through a background grid, and its particles carry their kernel functions along: it reassigns them here first, then lets its constraints follow.

Only the constraints that are switched on are located anew (switchedOn), those out of reach included, so that they can find themselves within reach again. A constraint switched off from outside rests until it is switched on again, and is located anew at the start of the next increment then.

A change of the coupling is not a change of the mesh: it neither moves nodes nor creates them, so a solver rebuilds its equation system, but does not re-equilibrate (equilibrateAfterModelChange).

Returns:

True if a coupling changed, so that the equation system has to be rebuilt.

Return type:

bool

EquationSystemLayout - What the equation system of a model is made of

What a model answers a solver that (re)builds its equation system: the numbering of the degrees of freedom, the elements to compute, and how the solution passes between the model and the solver’s vectors. See What the solver asks the model.

What the global equation system of a model is made of: the answer a model gives a solver that (re)builds its equation system, see buildEquationSystem() and What the solver asks the model.

class edelweissfe.models.equationsystemlayout.EquationSystemLayout(model, dofManager, elements)[source]

The layout of the global equation system of a model: which degrees of freedom it has, which elements contribute to it, and how the solution passes between the model and the vectors a solver iterates on.

A solver asks the model for it whenever it (re)builds its equation system (buildEquationSystem()), and keeps it as long as the numbering of the degrees of freedom it holds: until the next rebuild. The solver itself only solves; what the model is made of, the layout says.

This class is the layout of a finite element model. A model made of other entities – EdelweissMeshfree’s material point and RKPM models, with their background cells and particles – returns a layout derived from it, which changes what its methods do; the solver calls them the same way.

Parameters:

  • model (FEModel) – The model.

  • dofManager (DofManager) – The numbering of the degrees of freedom.

  • elements (list) – The elements, in the order in which the solver computes them.

updateMaterialPoints(dU, timeStep, forEachChunk)[source]

Bring the material points that belong to no element up to date with the trial solution increment, right before the solver computes the elements. Called whenever NIST, or a solver derived from it (NEST, NID), evaluates the elements (see assembleInternalForces()), e.g. in every Newton iteration and for every trial state of a line search. The explicit dynamic solver NED evaluates the elements of a finite element model itself, and does not call it.

The loops over the entities belong to the solver, as the loop over the elements does: forEachChunk(entities, work) calls work(chunk) for chunks that together hold all entities, in the calling thread or on the threads of a parallel solver (see forEachChunk()). A layout loops through it over entities that are independent of each other.

A finite element model has no such material points: every element evaluates the material at its own quadrature points, in computeKernels(), so there is nothing to do here. In the material point method, the material points move through a fixed background grid, and belong to the cell they currently lie in: here, each cell interpolates the solution increment to its material points, and the material points evaluate their material, before the solver computes the cells, which integrate the result.

Parameters:

  • dU (DofVector) – The trial solution increment.

  • timeStep (TimeStep) – The time step.

  • forEachChunk (Callable[[list, Callable], None]) – The solver’s loop over chunks of independent entities.

TopologyPipeline - How the mesh may change during a run

Held by every model as model.topology. The topology pipeline: how, and only how, the mesh of a model may change during a run.

class edelweissfe.models.topologypipeline.TopologyPipeline(model)[source]

Everything about changing the mesh of a FEModel during a run, held by the model as model.topology.

The model itself is the mesh and its data. This class is the machinery around changing it:

  • the topology window (changes()), the only scope in which elements and nodes may be created or removed;

  • the number allocators (reserveElementNumbers(), reserveNodeNumbers()), which make numbering a pure function of the creation order;

  • the fixed-point rounds (update()), in which every model modifier (e.g. AMR) plans and applies until none has anything left to do;

  • the change log (version, changesSince()) and the registry of mesh dependents (refreshMeshDependents()), from which ties and contact catch up;

  • the history of every applied decision, its fingerprint, and the replay of that history on restart (replayHistory()).

Parameters:

model – The model whose mesh this pipeline changes.

changes(deferFieldBookkeeping=False)[source]

The only scope in which elements may be created or deleted.

Opened once around model setup, and once per increment around the model modifiers. Outside it, createElement() and removeElement() raise – which is what makes “only model modifiers mutate the topology” an enforced property rather than a convention, and what lets reserveElementNumbers() guarantee that element numbering is a pure function of the ordered creation sequence.

Nesting is permitted and is a no-op for the inner scope: setup-time helpers may open a window without knowing whether their caller already did.

Parameters:

deferFieldBookkeeping (bool) – Postpone the node-field bookkeeping a mesh mutator requests through _resizeNodeFieldsForNodes() and _linkFieldVariableObjects() until this window closes, and run it exactly once then. Both are idempotent recomputations from the model’s current nodes and elements – neither one touches numbering, connectivity or anything the fingerprint() covers – so the state after one flush at the end equals the state after a flush per mutation; only the intermediate, immediately overwritten field layouts are skipped. That is what replayHistory() wants: no increment is solved between two replayed records, so nothing consumes those layouts, and a flush per record makes a long replay O(records x mesh) instead of O(mesh). The live per-increment window does not defer – the solver runs on the fields right after each update. Honoured by the outermost window only, like the window itself.

The ModelChange coalesced across every mutation recorded after version, or None if the model hasn’t changed since. A pull-based consumer compares its own last-seen version against version and, on a mismatch, reconciles from this, then adopts the new version as its own last-seen version.

checkModelModifierDomains()[source]

Refuse a model in which two modifiers claim the same element.

Run once, at the end of setup. Each modifier declares what it owns via declaredDomain(); an overlap means both will mutate the same element and each will end up holding stale references to the other’s work. Failing here costs a clear message at startup; failing later costs a corrupted element set or a node that is both Dirichlet-prescribed and an MPC slave, discovered mid-solve.

ensureSurfaceFacetModifier(journal)[source]

Create the implicit facet-regeneration modifier, if any facet recipe was declared.

Retiling a contact/tie surface creates and deletes elements, so it is a topology change and belongs in the topology-update phase – not in a consumer’s refresh, which is where it used to live and which is what made every tie a mutating consumer. Users never declare this modifier: they already declared the *surface recipe it acts on.

fingerprint()[source]

A short digest of the model’s topology and its numbering, for verifying that a restart replay reproduced the original run.

Covers exactly what a replay must get right and nothing else: every element’s number, type and connectivity (in order – a rotated connectivity is a real difference), and every node’s label and reference coordinates. The surface nodes of a discrete rigid body hold its current position instead; the body reports their reference coordinates (referenceCoordinatesOfMovedNodes()), so that the motion of a rigid body is not mistaken for a change of the mesh. A resumed run replays the topology before it restores the displacement, i.e. with the body still at its reference position. Deliberately excludes solution state, so a mismatch means the mesh diverged, not that the solver took a different path.

Recorded per round in the topology history, this turns “the resumed run diverged somewhere” into “increment 471, round 2, modifier amr” – a divergence you can bisect rather than hunt.

Not cheap: it walks the whole mesh, measured at 0.188 s on 64k elements / 69k nodes. A live run pays it once per applied modifier decision, in recordChange(). A replay pays it once for the whole history (replayHistory() carries the recorded digests forward and checks the final one), unless verifyFingerprintsPerRecord asks for the per-record walk to locate a divergence.

Uses blake2b rather than hash(), whose string hashing is randomised per process and would make the digest differ between two runs of the same code.

Returns:

A 32-character hex digest.

Return type:

str

recordChange(roundNumber, name, modifier, plan, modelChange, time=None, fingerprint=None)[source]

Register everything an applied decision produced: the replay record and the changeset.

Two things are recorded here, deliberately in one place:

  • an entry in history, holding the plan in the modifier’s own serializable form plus the resulting topology fingerprint – which is what lets a resumed run be checked round by round instead of only at the end;

  • the modelChange itself, stamped with the next version, so changesSince() and refreshMeshDependents() can see it.

A model modifier therefore reports what it did in exactly one way: by returning a ModelChange from apply() – there is no second channel to keep in sync, and so no way to update one and forget the other.

Both callers of apply (the live update() loop and replayHistory()) route through here, so a replayed run records the same changesets in the same order as the run it replays.

Cost is one fingerprint() per applied decision – not per iteration, but not free either: 0.188 s measured on 64k elements / 69k nodes – unless the caller supplies the fingerprint, which a replay does (see replayHistory()).

Parameters:

  • time (float) – Model time to stamp the record with. Defaults to the current time; a replay passes the recorded time instead, so a resumed run’s history carries the times the decisions were originally made rather than the time it was resumed at.

  • fingerprint (str) – The digest to record. Defaults to fingerprint() of the model as it is now, which is what a live run wants. A replay passes the digest the original run recorded, so the replayed history carries the digests that were verified rather than fresh ones that would launder a divergence into the next checkpoint.

  • roundNumber (int)

  • name (str)

Return type:

TopologyRecord

refreshMeshDependents()[source]

Let every registered mesh-dependent consumer catch up, once, after the topology update.

Phase 2 of the increment (see update() for phase 1). Consumers are pure readers here – the topology window is closed – so their order does not matter and no fixed-point iteration is needed: none of them can invalidate another’s work.

Each consumer sees the net change across every round of the topology update, which is why this is pull and not push: a push fires per mutation, i.e. at moments that are by construction mid-pipeline, handing a consumer a state that no longer exists by the time the solve begins.

Returns:

True if any consumer reported that its DOF footprint changed.

Return type:

bool

registerMeshDependent(consumer)[source]

Register a MeshDependent to be refreshed after every topology update.

Registration is the freshness guarantee: a consumer that is not in this list is never told the mesh changed. That matters most for the consumers the solver does not otherwise tick – multi-point constraints live in model.multiPointConstraints, which no per-increment sweep iterates, so a tie could only ever learn about refinement this way.

replayHistory(records, journal=None)[source]

Reconstruct the topology by re-applying recorded decisions, in order.

This is the whole point of the plan/apply split: the modifier’s apply() runs here exactly as it did live, fed a decoded plan instead of a freshly evaluated one. There is no replay-specific code path to drift from the live one – which is what the previous design had, and why a resumed run silently renumbered its elements.

What a replay does not repeat per record is the whole-mesh work around apply whose result is a pure function of the final mesh: the fingerprint() walk (the recorded digests are carried forward and the final one is checked) and the node-field bookkeeping (deferred to the end of the window, see changes()). A history of a few hundred refinements on a mesh of tens of thousands of elements replayed in minutes otherwise, all of it spent re-deriving state that the next record, or readRestart(), overwrote right away.

Parameters:

  • records – The TopologyRecord sequence to replay.

  • journal (Journal) – Optional Journal for progress messages.

Raises:

TopologyError – If the replayed topology’s fingerprint differs from the one recorded with the last record (when verifyFingerprints). With verifyFingerprintsPerRecord every record is checked as it is replayed and the error names the first diverging one – so a divergence is located rather than merely detected.

reserveElementNumbers(count=1)[source]

Reserve count fresh element numbers.

The allocator is monotonic: numbers are never recycled, and are never derived from max(self._model.elements). Both properties matter beyond tidiness.

Deriving the next number from max(self._model.elements) makes numbering a function of the deletion history as well as the creation history – a contact facet set that is deleted and rebuilt (the common case between two refinements) hands the freed numbers straight back out – so a restart replay would have to reproduce creations, deletions and their interleaving to renumber identically. With one monotonic counter it only has to reproduce the ordered creation sequence, which is exactly what the recorded topology history holds.

Never recycling additionally means a number refers to one element for the model’s entire lifetime, so mergedWith()’s documented no-reuse assumption holds, and a reference cached by number cannot silently alias a different element.

Parameters:

count (int) – How many consecutive numbers to reserve.

Returns:

The reserved numbers, in ascending order.

Return type:

range

reserveNodeNumbers(count=1)[source]

Reserve count fresh node labels. The node-side counterpart of reserveElementNumbers(), monotonic for the same reasons.

The pattern this replaces is len(model.nodes) + 1, which is a positional guess, not an allocator: once anything is deleted the dict has gaps, and the “next” label lands on a live node and silently overwrites it.

update(step=None)[source]

Run every model modifier to a fixed point, inside one topology window.

Modifiers depend on each other – refinement invalidates a tied surface’s facets, a deposition modifier creates elements refinement may then want to split, and a 2:1 balance may need to refine what another modifier just activated. Rather than asking the user to declare a dependency order (which cannot express mutual dependence anyway), each round offers every modifier the net change since that modifier last planned. A round in which nobody plans anything is the fixed point.

Determinism comes from the round structure, not from luck: within a round, modifiers run in self._model.modelModifiers order, which is input-file order.

Returns:

True if the topology changed, so the solver rebuilds its equation system.

Return type:

bool

Raises:

TopologyError – If the rounds do not settle within maxRounds, which means some modifier keeps planning in response to its own output. The message names the offenders.
