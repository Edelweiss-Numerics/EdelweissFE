Step actions

Step actions define actions run during a simulation. They are defined within a *step definition, line by line, by specifying their name and a list of option=value, for example

*step, solver=mySolver
>>dirichlet, name=bottom,   nSet=bottom,   field=displacement, 2=0, 1=0
>>dirichlet, name=rightTop, nSet=rightTop, field=displacement, 2=0,
>>distributedload, name=dload1, surface=top,  type=pressure, magnitude=10, f(t)=t*2
>>distributedload, name=dload2, surface=left, type=pressure, magnitude=50, f(t)=t

changematerialproperty - Change a material property during a step

Relevant module: edelweissfe.stepactions.changematerialproperty

Change a property of a material during a step.

At the start of every increment, one entry of the material’s property vector is set to a value prescribed as a function of the step time, for every element of every section using the material. The elements keep their state: a changed property affects how the state evolves from then on, but the state accumulated so far (stress, plastic strain, damage, …) is neither reset nor re-initialized. Properties an element was assigned individually (materialParameterFromField) are kept, apart from the changed one.

classmethod fromStepActionDefinition(name, definition, jobInfo, model, fieldOutputController, journal)[source]

Create this step action from a parsed .inp step action definition.

This is the one place a module’s input-file shape (numbered component options, a f(t) expression string, a node set name) is turned into the typed arguments its real constructor takes. Override it together with a typed __init__; leave it alone and the default dict-consuming constructor is used unchanged.

Parameters:

  • name (str) – The name of the step action.

  • definition (dict) – The parsed option mapping for this step action.

  • jobInfo (dict) – A dictionary containing the information about the job.

  • model (FEModel) – The model tree.

  • fieldOutputController (FieldOutputController) – The field output controlling object.

  • journal (Journal) – The journal object for logging.

Implementing your own loads

A load is a step action that derives from LoadBase and assembles its own contribution to the equation system in assembleLoad: the negative of the external load it applies, and the tangent of that contribution, nonzero only for a load that follows the deformation (see The residual and the tangent). The solvers do not need to know what a load acts on; their assembleLoads only loops over the loads of the step and lets each assemble itself. They find the loads by this base class, whatever step action module defines them: a load module of its own, registered like any step action, needs no change to any solver, and an arc length step scales it at its end like any other load.

Three bases implement assembleLoad once for all loads of their kind, so that a load deriving from them only says how large it is at a time (getCurrentLoad) and where it acts:

  • NodalLoadBase: concentrated loads on the degrees of freedom of a field on a node set, such as nodeforces;

  • DistributedLoadBase: loads per unit area on the faces of a surface, which every element integrates over its loaded face, such as distributedload;

  • BodyLoadBase: loads per unit volume, which every element of an element set integrates over its volume, such as bodyforce.

A load that acts on something else – the cells or particles of a meshfree model, say – derives from LoadBase directly.

class edelweissfe.stepactions.base.loadbase.LoadBase(name, definition, jobInfo, model, fieldOutputController, journal)[source]

A load: a step action that adds the residual contribution of the external load it applies – the negative of that load, see The residual and the tangent – and the tangent of that contribution, which is nonzero only for a load that follows the deformation.

Every load assembles its own contribution in assembleLoad(), wherever it acts: a node force goes to the degrees of freedom of its nodes, a distributed load or a body force asks each of its elements for the integral over the loaded face or volume. A solver therefore only loops over the loads, see assembleLoads(), which it finds among the step’s actions by this base class, whatever step action module holds them (see collectLoads()): a new kind of load – one acting on the cells or particles of a meshfree model, say – needs no change to any solver.

Over a step, a load changes along its amplitude \(a(t)\), from its value at the start of the step, \(f(0)\), to \(f(1)\) at the end; at the end of the step it keeps the value it reached, from which the next step starts (see applyAtStepEnd()).

static amplitudeAtStepEnd(amplitude, loadParameter)[source]

The value of a load’s amplitude at the end of a step, by which the load keeps the change the step declared.

A step that follows the amplitudes ends at the end of the amplitude, \(a(1)\). An arc length step scales the change of every load over the step, \(f(1) - f(0)\), by its load parameter \(\lambda\), and so it ends on the straight line from the start to the end of the amplitude:

\[a(0) + \lambda \, \left( a(1) - a(0) \right).\]

With the default linear amplitude, this is the load parameter itself. A load the step holds at a constant amplitude, e.g. a self-weight declared with f(t)='1', is part of the dead load of the arc length step, and keeps its full value, whatever the load parameter.

Parameters:

  • amplitude (Callable[[float], float]) – The amplitude of the load over the step progress interval [0...1].

  • loadParameter (float | None) – The load parameter an arc length step ended at; None for a step that follows the amplitudes.
