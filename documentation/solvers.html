Solvers

Currently, EdelweissFE provides

  • a nonlinear implicit static solver (NIST),

  • a nonlinear explicit static solver (NEST),

  • a nonlinear explicit dynamic solver (NED),

  • a nonlinear implicit dynamic solver (NID, Newmark-beta time integration),

  • a parallel nonlinear implicit static solver (NISTParallel),

  • a parallel nonlinear explicit static solver (NESTParallel),

  • a parallel nonlinear explicit dynamic solver (NEDParallel),

  • a parallel nonlinear implicit dynamic solver (NIDParallel),

  • and a parallel arc length solver (NISTPArcLength).

Choose the solver in the *solver definition:

*solver, name=mySolver, solver=NISTParallel
edelweissfe.config.solvers.getSolverByName(name)[source]

Get the class type of the requested solver.

Resolved through the registry (solver category) rather than through a hand-maintained table private to this module. Such a table could only ever list solvers living inside this package, so an external package – EdelweissMeshfree, a plugin – had no way to contribute one; going through the registry means a built-in, an entry point and an in-process register() call are all equally reachable here. An unknown name now raises RegistryLookupError naming the available solvers, instead of a KeyError.

Solver names are now case-insensitive, deliberately. This resolver was the one case-sensitive registry in the codebase: it indexed a table with CamelCase keys and then read the class off the module under the same string, so the name doubled as the class attribute name and e.g. "nist" failed twice over, while 12 of the 13 legacy config/*.py registries already casefolded the name at the resolver. That audit amends rule (c) to sanction this: a name must not resolve differently depending on which front-end it arrived through, and the registry is reached by callers with no .inp parser in the loop. The change is strictly more permissive, so no existing input file changes meaning.

The residual and the tangent

Every entity that enters the equation system – an element, a load, a constraint – contributes two things: a vector \(\boldsymbol{P}\) to the residual, and its tangent \(\boldsymbol{K} = \partial \boldsymbol{P} / \partial \boldsymbol{U}\). The rule is the same for all of them:

  • An element adds its internal forces, \(\boldsymbol{P} = \boldsymbol{f}_\mathrm{int} = \int_\Omega \boldsymbol{B}^T \boldsymbol{\sigma} \, \mathrm{d}V\), and its stiffness matrix.

  • A load adds the negative of the external load it applies: a node force \(\boldsymbol{F}\) adds \(-\boldsymbol{F}\), a body force \(-\int_\Omega \boldsymbol{N}^T \boldsymbol{b} \, \mathrm{d}V\). A dead load has no tangent; a load that follows the deformation, such as a pressure on the current surface, has one.

  • A constraint adds the negative of the force it exerts on its nodes – just what an element of the same mechanics would add as its internal force. A penalty spring of stiffness \(k\) that pulls a degree of freedom \(u\) towards \(\bar{u}\) adds \(P = k\,(u - \bar{u})\) and \(K = k\); a Lagrange multiplier \(\boldsymbol{\lambda}\) enforcing \(\boldsymbol{g}(\boldsymbol{u}) = \boldsymbol{0}\) adds \(\boldsymbol{\lambda}^T \partial \boldsymbol{g} / \partial \boldsymbol{u}\) to the rows of the nodes and \(\boldsymbol{g}\) to the rows of the multipliers. See Constraints for writing one.

A solver sums the contributions in three loops of every iteration: computeElements over the elements, assembleLoads over the loads – every load assembles its own contribution, wherever it acts (see LoadBase) – and assembleConstraints over the constraints that are active (see Constraints). Summed over all entities,

\[\boldsymbol{G}(\boldsymbol{U}) = \sum \boldsymbol{P} = \boldsymbol{f}_\mathrm{int} - \boldsymbol{f}_\mathrm{ext}\]

is the out-of-balance force, which equilibrium makes zero, and the summed \(\boldsymbol{K}\) is its derivative. Newton’s method replaces \(\boldsymbol{G}(\boldsymbol{U} + \Delta \boldsymbol{U}) = \boldsymbol{0}\) by its linearization \(\boldsymbol{G} + \boldsymbol{K}\, \Delta \boldsymbol{U} = \boldsymbol{0}\), so the implicit solvers solve

\[\boldsymbol{K}\, \Delta \boldsymbol{U} = \boldsymbol{R}, \qquad \boldsymbol{R} = -\boldsymbol{G} = \boldsymbol{f}_\mathrm{ext} - \boldsymbol{f}_\mathrm{int}\]

in every iteration. The right-hand side \(\boldsymbol{R}\) is what the convergence criteria check, and what the multi-point-constraint condensation and the Dirichlet boundary conditions act on. The other solvers use the same sums:

  • NID subtracts the inertia and damping forces from \(\boldsymbol{R}\), and adds their tangents to \(\boldsymbol{K}\).

  • NED accelerates the nodes with the net force \(\boldsymbol{R}\), and needs no tangent.

  • NISTPArcLength sums the loads twice, at the start of the step (the dead load, \(\boldsymbol{P}_0\)) and at its end; their difference is the reference load, \(\boldsymbol{P}_\mathrm{ref}\). Scaled by the load parameter \(\lambda\), it enters \(\boldsymbol{R} = -(\boldsymbol{P}_0 + \lambda \boldsymbol{P}_\mathrm{ref} + \boldsymbol{P}_\mathrm{elements} + \boldsymbol{P}_\mathrm{constraints})\).

Why one rule? Because then \(\boldsymbol{K}\) is always the derivative of exactly what was added to \(\boldsymbol{P}\), for every entity alike. That can be checked by finite differences, entity by entity, and the same check catches a contribution whose sign alone is wrong: \(\boldsymbol{K}\) then comes out as \(-\partial \boldsymbol{P} / \partial \boldsymbol{U}\). A contribution negated together with its tangent passes it, so tests/test_residual_tangent_convention.py checks every constraint this way and also checks the direction of the forces it exerts (see Constraints); a dead load has no tangent, so there the sign of each element load is checked against the load integrated independently.

The elements’ sum alone, \(\boldsymbol{f}_\mathrm{int}\), is what the implicit solvers and NEST report as the nodal result P of a field output: at a degree of freedom with a Dirichlet boundary condition and no load, it is the reaction force. NED reports its net force \(\boldsymbol{R}\) there.

What the solver asks the model

A solver solves; what the equation system is made of, the model says. NIST, NISTParallel and NISTPArcLength ask the model three questions, and know nothing of their own about what a model consists of:

  1. Has the coupling of the degrees of freedom changed? At the start of every increment, and of every retry after a cutback, the topology update calls updateConnectivity(), before the increment is proposed. If a coupling changed, the solver rebuilds its equation system before it solves the increment. A change of the coupling is not a change of the mesh: no node moves or appears, so the solver does not re-equilibrate after it (equilibrateAfterModelChange), and it keeps its prediction if the rebuilt system numbers the degrees of freedom as before (extrapolateAcrossConnectivityChange).

  2. What is the equation system made of? Whenever the solver (re)builds its equation system, it calls buildEquationSystem(), which returns the layout of the system, an EquationSystemLayout. The solver keeps it as long as the numbering of the degrees of freedom it holds – until the next rebuild – and takes from it:

    • the numbering of the degrees of freedom (the DofManager). It also locates the degrees of freedom of a field on a node set, those a Dirichlet boundary condition prescribes or a node force loads (locateFieldOnNodeSet());

    • the elements, a list of everything the solver computes like an element (computeElements);

    • where the solution vector starts from after a rebuild, and where the results of a converged increment go;

    • the model the linear solver is set up for.

  3. Is anything to be updated before the elements are computed? In every evaluation of the model – every Newton iteration, every trial state of a line search – the solver assembles the internal forces (assembleInternalForces()): it calls updateMaterialPoints(), right before it computes the elements.

The loops over the entities stay with the solver: NIST computes the elements one after the other, NISTParallel on all threads, each element into its own part of the residual and its own block of the system matrix (see System matrix assembly). A layout that updates material points loops over them through the solver’s forEachChunk(), so that they are evaluated on the same threads.

The other solvers ask a part of these questions. NID and NEST derive from NIST, and build, fill and write back their equation systems through the layout; NEST builds its system once per step and has no topology update, and NID assembles its mass matrix from the model’s finite elements. NED takes only the numbering of the degrees of freedom from the layout, and evaluates the model’s finite elements in its own loop.

A finite element model answers as follows: its constraints update the nodes they couple (a contact constraint searches for the surface it touches); its equation system numbers all nodes and the active constraints with their scalar variables; its elements are the finite elements; every node carries its total solution from increment to increment; and nothing is to be updated before the elements, which evaluate the material at their quadrature points themselves.

A model of EdelweissMeshfree answers differently, with the same solvers:

  • Its material points move through a fixed background grid of cells, and its particles carry their kernel functions along. When asked for the coupling, it first assigns the material points to the cells they lie in and the particles to the kernel functions they reach, then lets its constraints follow.

  • Only the part of the grid that holds material points, and the nodes in reach of the particles, form the equation system (the active domain). So a node set of the grid may reach beyond the equation system: a Dirichlet boundary condition then prescribes, and a node force loads, the nodes of the set in the active domain.

  • Its elements are its finite elements, the active cells, and the particles.

  • Only finite element nodes carry a total solution from increment to increment. The material point method and RKPM are incremental on the current configuration – the cells are reset and the kernel functions move with their particles, while the state lives in the material points and particles – so the values at the nodes of the grid and of the kernel functions are coefficients of one increment, and start every rebuilt equation system at zero.

  • Before the cells are computed, each cell interpolates the solution increment to its material points, and the material points evaluate their material; the cells then integrate the result.

quadraticLineSearch(largestResidualAt)[source]

The step length \(\alpha\) by which a Newton correction is scaled, for a Newton iteration that overshoots or oscillates (e.g., materials switching between loading and unloading).

The largest residual along the correction, \(\| R(\alpha) \|_\infty\) with the Dirichlet degrees of freedom left out, is evaluated at the trial step lengths lineSearchStepLengths, and a parabola is fitted to these values (least squares for more than three). The step length minimizes the parabola on lineSearchStepLengthRange: it is the vertex of a parabola that opens upwards, limited to that range, and otherwise the end of the range where the parabola is smaller. Each trial costs one evaluation of the model; the next Newton iteration evaluates the chosen one.

Two kinds of trials fit no parabola:

  • A trial state at which the residual is not finite, which the model could not evaluate: the trials decide themselves, and the step length is the trial step length of the smallest finite residual (of equal ones, the shortest), limited to the range. If no trial residual is finite, the increment is cut back.

The trial states are those setTrialState() sets: the solution increment moved along the correction \(\Delta\Delta U\), and, under arc length control, the load parameter moved with it, such that every trial state satisfies the controller’s equation (see setTrialState()).

The arc length method (Jirásek/Bažant 2001): a step’s reference load is scaled by a load parameter \(\lambda\), which is an unknown of every increment besides the solution, and which a controller step action determines, e.g. such that a crack opening grows steadily. Paths with snap-back or snap-through, which neither a prescribed load nor a prescribed displacement can follow, are traced this way.

The controller is the step action of the step that the option arcLengthController names (see ArcLengthControllerBase); without one (arcLengthController=off), the step is solved as by NISTParallel.

The Newton iterations are those of solveIncrement(); the load parameter enters them through its hooks: the prediction (extrapolateLastIncrement()), the loads of the evaluated state (assembleLoadsAtIncrementEnd()), the first iterate (firstIterateNeedsCorrection()), the linear solve for two right-hand sides (solveForCorrection()), and the corrections of the pair of the solution and the load parameter (setTrialState(), applyCorrection()).

Every arc length step scales its own reference load – the change of its loads and prescribed displacements over the step – from \(\lambda = 0\), so it starts from the loads the steps before it ended with; at its end, every load keeps the value the step applied (see applyStepActionsAtStepEnd()). The load parameter of the step being solved is published as model.additionalParameters["arc length parameter"], e.g. for a load-displacement curve.

The re-equilibration after a model change (option equilibrateAfterModelChange) is an arc length increment of size zero, solved by solveIncrement() like any other: the controller’s equation asks for a change of zero, so the controlled quantity stays where the last accepted increment left it, and the load parameter is solved for, and with it the loads and the prescribed degrees of freedom it scales. This is what a zero-time re-equilibration holds under displacement control, and, unlike a constant load, it has a solution past a limit point. As for any increment, the stop condition is checked before it, and the controller’s finishIncrement is called once it has converged; the load parameter it reaches, committed with its state, is the one the next increment starts from.

Newton’s method for the solution increment and the increment of the load parameter together: the iterations of solveIncrement(), into which the load parameter enters through the hooks of this class.

Each iteration evaluates the model at the iterate (with the loads of assembleLoadsAtIncrementEnd()), and solves the linearized system for two right-hand sides at once: the out-of-balance force \(R_0\), and the reference load \(R_f\) (solveForCorrection()). Arc length control

A load-controlled analysis cannot pass a limit point: beyond the peak of the load, no larger load is in equilibrium. A displacement-controlled one cannot follow a path that snaps back, where the controlled displacement decreases again. The arc length method (here the indirect displacement control of Jirásek and Bažant) controls neither the load nor a displacement directly. The external load of a step becomes

\[\boldsymbol{f}_\mathrm{ext} = \boldsymbol{f}_0 + \lambda \, \boldsymbol{f}_\mathrm{ref},\]

the loads at the start of the step (the dead load \(\boldsymbol{f}_0\)) plus the change of the loads over the step (the reference load \(\boldsymbol{f}_\mathrm{ref}\)) scaled by a load parameter \(\lambda\), which is an unknown of every increment besides the solution. A controller adds the equation that determines it, typically that a combination of displacements – a crack opening, the mean contraction of a tunnel ring – grows steadily over the step. Every Newton iteration solves the linearized system for two right-hand sides at once, the out-of-balance force and the reference load, and the controller combines the two corrections into the correction of the solution and of the load parameter. The Newton iterations are those of NIST, into which the load parameter enters through the hooks of the solver (see its class documentation above). Every arc length step scales its own reference load: its load parameter starts from zero, where the external load is the dead load – the loads the steps before it ended with. An analysis that continues under arc length control in a later step declares there the change of the loads it applies on top of them.

Prescribed displacements belong to the reference loading of the step, like the loads: a Dirichlet boundary condition that prescribes a change \(\Delta\bar{\boldsymbol{u}}\) over the step moves its degrees of freedom by \(\lambda \, \Delta\bar{\boldsymbol{u}}\). They move with the load parameter, and only with it. The reference solve carries \(\Delta\bar{\boldsymbol{u}}\) in their rows, so a correction \(\Delta\Delta\lambda\) moves them by \(\Delta\Delta\lambda \, \Delta\bar{\boldsymbol{u}}\); eliminating their columns turns \(\Delta\bar{\boldsymbol{u}}\) into the forces it takes to impose it, which join the reference load. The out-of-balance solve leaves them where they are. So the prescribed degrees of freedom are no unknowns of Newton’s method, and their rows, which hold no equation, are left out of the convergence check, as in NIST. A predicted increment places them where the predicted load parameter puts them.

At the end of an arc length step, every load keeps the value the step applied, \(f(0) + \lambda \, (f(1) - f(0))\), from which the next step starts. With its amplitude \(a(t)\), a load keeps the change it declared for the step scaled by \(a(0) + \lambda \, (a(1) - a(0))\) (see LoadBase): a load ramped linearly over the step keeps \(\lambda\) times its change, and a load the step holds at a constant amplitude, such as a self-weight declared with f(t)='1', is part of the dead load and keeps its full value, whatever the load parameter.

The controller is a step action of the step, e.g. an indirectcontrol, and the solver option arcLengthController names it (off, the default, solves the step without arc length control):

*step, solver=theSolver
maxInc=1e-2, startInc=1e-2, minInc=1e-6, maxNumInc=1000, maxIter=25
>>options, name=theSolver, arcLengthController=opening
>>indirectcontrol, name=opening, dof1='model.nodeSets["IDC1"][0].fields["displacement"]', cVector1='-1, 0', dof2='model.nodeSets["IDC2"][0].fields["displacement"]', cVector2='1, 0', L=0.01

From Python, without an input file, the controller is a step action built through its typed constructor, and the option is a constructor argument of the solver:

stepActions["indirectcontrol"]["opening"] = IndirectControl("opening", dof1, dof2, [-1.0, 0.0], [1.0, 0.0], 0.01, model, journal)
solver = NISTPArcLength(jobInfo, journal, arcLengthController="opening")

A step under arc length control may end before its time is up: the solver option stopCondition, an expression of the model and its field outputs, e.g. stopCondition='fieldOutputs["UTop"] < -1.0', is checked after every accepted increment of nonzero size, and the step ends once it is true. A stop condition belongs to the controller it is declared with: an >>options block that names arcLengthController (off too) without a stopCondition drops the one of an earlier step, so that a later step does not stop by the condition that ended the step before it:

>>options, name=theSolver, arcLengthController=opening, stopCondition='fieldOutputs["UTop"] < -1.0'

A stop condition in the *solver datalines belongs to the solver: every step whose >>options name a controller without a stop condition of their own returns to it. An >>options block that sets a stopCondition for a step without arc length control is refused, since the condition would never be checked.

The options of Newton’s method act on the pair of the solution increment and the increment of the load parameter \((\Delta U, \Delta\lambda)\):

  • extrapolation: both are predicted from the same accepted increments with the same weights, linearly or quadratically, so that the prediction stays on one extrapolated path; retryWithoutExtrapolation retries a failed increment from a zero prediction of both.

  • lineSearch: a line search scales the correction that the out-of-balance force causes, and the controller completes every trial state with the correction of the load parameter its equation asks for at that step length, as it completes the full correction. So every trial state satisfies the controller’s equation, and so does the iterate the line search chooses: the line search cannot leave the equation unsatisfied, also not from an iterate that does not satisfy it yet.

  • fallBackToQuasiNewton: the tangent of the first iteration serves both right-hand sides.

Every converged increment publishes the load parameter of its step as model.additionalParameters["arc length parameter"], e.g. for a load-displacement curve. The solver checkpoints the load parameter of the step and the increments of it its predictor extrapolates, the loads what they keep from step to step, and the controller the change of its controlled quantity over the step, so an arc length controlled run resumes exactly where it stopped.

The re-equilibration after a model change (equilibrateAfterModelChange, see Model modifiers) is, under arc length control, an arc length increment of size zero: the controller asks for a change of zero, so the controlled quantity stays where the last accepted increment left it, and the load parameter is solved for, and with it the loads and the prescribed displacements it scales – the counterpart of a zero-time increment under displacement control, which, unlike a constant load, has a solution past a limit point. As for any increment, the stop condition is checked before it, and the controller’s finishIncrement is called once it has converged. The load parameter it reaches is committed with its state, and the next increment starts from it.

NID - Nonlinear Implicit Dynamic (Newmark-beta)

The nonlinear implicit dynamic solver: Newmark-beta time integration on top of the Newton loop of NIST.

An increment solves the semi-discrete equation of motion

\[\boldsymbol{M} \ddot{\boldsymbol{u}}_{n+1} + \boldsymbol{C} \dot{\boldsymbol{u}}_{n+1} + \boldsymbol{P}_\mathrm{int}(\boldsymbol{u}_{n+1}) = \boldsymbol{P}_\mathrm{ext}(t_{n+1})\]

for the displacement at the end of the increment, with the velocity and the acceleration expressed through the displacement increment \(\Delta \boldsymbol{u} = \boldsymbol{u}_{n+1} - \boldsymbol{u}_n\) by the two Newmark relations (Newmark 1959; Hughes, The Finite Element Method, ch. 9)

\[\begin{split}\boldsymbol{u}_{n+1} &= \boldsymbol{u}_n + \Delta t \, \dot{\boldsymbol{u}}_n + \tfrac{\Delta t^2}{2} \left[ (1 - 2\beta) \, \ddot{\boldsymbol{u}}_n + 2\beta \, \ddot{\boldsymbol{u}}_{n+1} \right], \\ \dot{\boldsymbol{u}}_{n+1} &= \dot{\boldsymbol{u}}_n + \Delta t \left[ (1 - \gamma) \, \ddot{\boldsymbol{u}}_n + \gamma \, \ddot{\boldsymbol{u}}_{n+1} \right].\end{split}\]

Solved for the end-of-increment kinematics these read

\[\begin{split}\ddot{\boldsymbol{u}}_{n+1} &= \frac{\Delta \boldsymbol{u} - \Delta t \, \dot{\boldsymbol{u}}_n - \Delta t^2 \left( \tfrac{1}{2} - \beta \right) \ddot{\boldsymbol{u}}_n}{\beta \, \Delta t^2}, \\ \dot{\boldsymbol{u}}_{n+1} &= \dot{\boldsymbol{u}}_n + \Delta t \left[ (1 - \gamma) \, \ddot{\boldsymbol{u}}_n + \gamma \, \ddot{\boldsymbol{u}}_{n+1} \right],\end{split}\]

so that the effective residual and tangent handed to the Newton loop are

\[\begin{split}\boldsymbol{R} &= \boldsymbol{f}_\mathrm{ext} - \boldsymbol{f}_\mathrm{int} - \boldsymbol{M} \ddot{\boldsymbol{u}}_{n+1} - \boldsymbol{C} \dot{\boldsymbol{u}}_{n+1}, \\ \boldsymbol{K}_\mathrm{eff} &= \boldsymbol{K} + \frac{1}{\beta \, \Delta t^2} \boldsymbol{M} + \frac{\gamma}{\beta \, \Delta t} \boldsymbol{C}.\end{split}\]

Everything else – element evaluation, loads, constraints, multi-point-constraint condensation, Dirichlet handling, the convergence test, cutbacks and the linear solver – is the parent’s: this solver runs solveIncrement() itself and enters it only through its three hooks – NonlinearImplicitDynamic.initializeIncrement() (mass, damping, dynamic stiffness, initial acceleration), NonlinearImplicitDynamic.assembleAdditionalTerms() (two terms in the residual and two in the tangent, where the parent forms R = f_ext - f_int and before the tangent is converted to CSR) and NonlinearImplicitDynamic.finalizeIncrement() (the converged velocity and acceleration become the state).

Parameters. The default \(\beta = 1/4\), \(\gamma = 1/2\) is the average-acceleration (trapezoidal) rule: second-order accurate, unconditionally stable for linear problems and free of numerical damping, so the discrete energy of an undamped linear system is conserved exactly and any drift in it points at a bug rather than at the scheme. \(\gamma > 1/2\) adds algorithmic damping at the price of first-order accuracy; \(\gamma \geq 1/2\) together with \(\beta \geq (\gamma + 1/2)^2 / 4\) keeps the scheme unconditionally stable. A choice outside that region is accepted with a warning, \(\beta = 0\) (the explicit central-difference member of the family) is refused, because the formulation above divides by it.

Mass. The mass is the CONSISTENT one, \(\int_\Omega \rho N^T N \, dV\), assembled from computeConsistentInertia() into the very sparsity pattern the stiffness uses – both are scattered through the same VIJ layout of the DofManager, so adding \(\boldsymbol{M}/(\beta \Delta t^2)\) to the tangent is an entry-wise scaled addition of two value vectors, before the parent’s in-place CSR update, its multi-point-constraint condensation and its Dirichlet row replacement, all of which therefore act on the effective matrix without knowing it is one. For the same reason the mass is summed into CSR form by the stiffness’ own CSR generator. The damping \(\boldsymbol{C}\) is the diagonal each element reports through computeLumpedDamping; being diagonal, it is kept only as its nonzero entries and their positions in the same layout, not as a full value vector. Both are assembled in one loop over the elements (in chunks of elements on the thread pool, see Parallelization) when the equation system is (re)built – at a step’s start and after a topology change – not per Newton iteration. A rebuild caused only by a constraint changing its connectivity (a contact candidate list, which can change on every increment) leaves every element, and with it every element’s slot in the layout, where it was: the operators are then reused in the new layout rather than reassembled – see NonlinearImplicitDynamic._reuseMassAndDamping(). The one exception is a step that changes a material property mid-step (>>changematerialproperty), which invalidates the density and makes them reassemble every increment.

Checks on the mass. The assembled mass and damping are checked at runtime for non-finite entries, the damping for negative entries, and every time-integrated degree of freedom for a nonzero mass; the total mass of each field is reported. The symmetry of the mass is not checked at runtime – on the assembled matrix that costs a transposed copy of it, gigabytes on a large model – but pinned once per element type in tests/test_nid_element_mass.py, together with the total mass \(\rho V\). It does matter: a non-symmetric mass still converges, to a wrong response. That test covers only the element types it lists – the Marmot hexahedra C3D8, C3D20, C3D20R and the gradient-enhanced GC3D8, GC3D20R; any other element type (the plane elements, for one) is not guarded anywhere, so add it to that list before using it with this solver.

Which fields. Only the fields whose inertia is a mass (carriesLinearMomentum(), i.e. the displacement) are integrated in time. Rows and columns of the mass and the damping belonging to any other field are zeroed, and those fields keep the parent’s quasi-static treatment. A nonzero inertia an element reports there – a rotational inertia, or the micro-inertia of a gradient-enhanced element – is discarded with a warning, once per field. A model with no such field is refused.

Zero-length and negligible increments. The time stepper proposes a zero-length increment before the first real one of every step. A quasi-static solver equilibrates it; this solver skips it with the state kept, because in zero time nothing can move: displacement and velocity are continuous, and a load appearing at that instant is answered by the acceleration below, not by a displacement. Solving it statically would put a suddenly loaded model at its static deflection before the first real increment – the whole dynamic response skipped. An increment shorter than \(10^{-10}\) of the time elapsed in the step is skipped for the same reason: it is the round-off remainder the stepper’s progress accumulation leaves at the end of a step (400 increments of 0.0025 leave 2e-14), and the Newmark update would divide by its square.

Initial acceleration. At the start of a step the acceleration is computed from equilibrium, \(\boldsymbol{M} \ddot{\boldsymbol{u}}_0 = \boldsymbol{P}_\mathrm{ext}(t_0) - \boldsymbol{P}_\mathrm{int}(\boldsymbol{u}_0) - \boldsymbol{C} \dot{\boldsymbol{u}}_0\), with the loads evaluated at the step’s own start (an f(t) amplitude at \(t = 0\)). Without it, a load applied suddenly at the start of a step would enter the trapezoidal rule as though it were zero at \(t_0\), which costs one first-order error in the momentum, and the scheme’s second order is lost. It is computed in the first real increment of the step. A step that continues from a restart checkpoint – a resumed run, or a step that falls back to one – therefore computes it only if the checkpoint was written before that, after the zero increment: every later checkpoint carries the acceleration, and recomputing it would replace a consistent state with one that agrees only to solver tolerance. Switch it off with computeInitialAcceleration=False to continue a step from whatever acceleration was carried over.

State and restart. Velocity and acceleration are ordinary node-field entries, V and A, written after every converged increment alongside the parent’s U/P/dU – the same mechanism the explicit solver uses for its velocity. That makes them part of every checkpoint the *output, type=restart manager writes and of every *fieldOutput (result=V, result=A), with no solver-specific restart code beyond the marker of whether the initial acceleration is still to be computed.

Live h-adaptivity. A *modelModifier, type=hAdaptivity refining the mesh mid-step is supported. Three things make that work, and only the third is this solver’s own:

  • Being node-field entries, V and A are carried onto the nodes a refinement creates by the same isoparametric interpolation from the parent element that already carries U (WARM_STARTED_NODE_FIELD_ENTRIES). Nothing here interpolates anything itself.

  • The mass and the damping are not transferred at all: they are reassembled from the elements that now exist, because the parent rebuilds its DofManager on a topology change and everything bound to it is rebuilt with it. There is therefore no re-lumping error of the kind an explicit solver has to account for – the total mass is an assembly of the new mesh, not a redistribution of the old.

  • The interpolated acceleration is only as good as an interpolation of the previous mesh’s acceleration, and it is not in equilibrium with the operators that were just reassembled. So the increment after a topology change recomputes the acceleration from equilibrium, with the cold-start machinery a step start already uses (computeInitialAcceleration, which also switches this off). The displacement and the velocity are kept: they are the kinematic state, and interpolation is the best statement of them the new mesh admits. Only a change that the topology pipeline actually recorded re-arms it – a mere change of a constraint’s connectivity (a contact candidate list) rebuilds the equation system without moving a node, and must not restart the acceleration of every degree of freedom in the model.

What is exactly conserved across a refinement, and what is not, is reported at every event and follows from the same partition-of-unity argument the explicit solver’s own live-adaptivity notes make: the assembled total mass is a geometric identity (children tile their parent at the same density) and is asserted; the linear momentum and the kinetic energy are exact for a spatially uniform velocity field and differ at second order in the velocity gradient across a refined parent otherwise, which is discretisation error rather than a defect, and are reported only. Unlike an explicit run, the increment that follows re-establishes equilibrium by Newton iteration, so an imbalance the transfer leaves behind is absorbed rather than radiated.

Prescribed motion. On a degree of freedom with a Dirichlet condition the acceleration is the one the Newmark relations imply for the prescribed displacement history, starting from zero at the step’s start. For a prescribed displacement that is not smooth in time – a velocity ramp switched on suddenly – the average-acceleration rule answers with an acceleration that oscillates from increment to increment on those degrees of freedom, and the consistent mass, having off-diagonal entries, passes the corresponding inertia forces on to the free neighbours. A smooth amplitude, or some algorithmic damping (newmarkGamma > 1/2), keeps that out of the response.

Not supported in this version. Rayleigh or any other damping model beyond what the elements report as their lumped damping; elements without a consistent mass (the pure-Python element library), which are refused at the first increment.

The time increment is the step’s increment (stepLength times the step-progress increment), so a constant dt is obtained with startInc = maxInc; a cutback shrinks it like any other implicit increment. The velocity and acceleration are available to every *fieldOutput as result=V and result=A on the displacement field, and travel with the *output, type=restart checkpoints, which is what makes a resumed run continue the same trajectory rather than restart it from rest.

NIDParallel is the same solver with the element loop evaluated in parallel (see below). The mass and the damping are assembled at a step’s start and after every topology change; when a contact constraint merely changes its connectivity, they are reused in the rebuilt equation system instead, which matters for contact problems whose candidate lists change on nearly every increment.

Reduced-integration elements (C3D20R, GC3D20R, …) need a Marmot whose consistent mass is integrated with the full rule of the element shape (Marmot PR #101): with the element’s own reduced rule the mass is singular, and the equilibrium solve for the initial acceleration with it.

The material must report a density (for LinearElastic, the third material parameter): the mass is assembled from it, and a time-integrated degree of freedom that receives none is refused rather than integrated as though it had inertia.

A *modelModifier, type=hAdaptivity refining the mesh mid-step is supported: V and A are carried onto new nodes by the node-field warm start, the mass and damping are reassembled on the refined mesh, and the acceleration is re-solved from equilibrium on the increment that follows – see Model modifiers, “Refinement under a dynamic solver”, for what is conserved exactly across such an event and what is not.

Verified in tests/test_nid_newmark.py, tests/test_nid_restart.py and tests/test_nid_amr.py against the exact discrete Newmark recurrence of the same problem, against the continuous closed form at second order, for exact conservation of the discrete energy, for restart equivalence of U, V and A, and – under live refinement – for exact transfer of a velocity field of degree at most one onto new nodes together with exact conservation of mass, momentum and kinetic energy in that case.

NIDParallel - Nonlinear Implicit Dynamic (Newmark-beta, parallel)

Parallel implementation of the NID solver.

The dynamics add nothing to the element loop, so the parallel variant is the serial one with NISTParallel’s thread-parallel computeElements mixed in. The method resolution order NIDParallel -> NID -> NISTParallel -> NIST routes every super() call of NID through NISTParallel, so both the Newton loop and the initial-acceleration solve evaluate the elements in parallel.

Prediction of an increment in the implicit solvers

Newton’s method starts each increment from a prediction of its solution increment. The solver option extrapolation chooses it:

  • off: from zero, i.e., from the last converged state.

  • linear (default): the last accepted increment, scaled to the size of the new one. The path of the solution is continued along its last secant.

  • quadratic: the parabola through the last three accepted states, evaluated at the end of the new increment, which continues the path along its curvature, too. For a solution that grows quadratically with the load, the prediction is exact, and the increment converges without a correction. While only one increment of the step of nonzero size has been accepted, the prediction is linear.

Sizes are measured in step progress. The prescribed degrees of freedom take their prescribed increment, so the first iteration of a predicted increment already checks convergence. Under arc length control, the increment of the load parameter is predicted from the same accepted increments with the same weights, see Arc length control.

A prediction can lead Newton’s method astray, e.g., when the path turns sharply. Two options decide what happens then and around rebuilds of the equation system, both off by default:

  • retryWithoutExtrapolation: if an extrapolated increment fails, it is attempted once more from a zero prediction before it is cut back. A failed increment then keeps the accepted history, and the smaller increment after the cutback is extrapolated from it as well. Without this option, a failed increment drops the prediction, and the increments up to the next accepted one start from zero.

  • extrapolateAcrossConnectivityChange: a change of the connectivity, e.g., a contact search that couples other nodes, rebuilds the equation system, and the increment starts from zero. With this option, it is extrapolated nevertheless, as long as the rebuilt system numbers the degrees of freedom exactly as the one the last increments were accepted in (compared by the digests of the two numberings, dofNumberingDigest): the last accepted increments are vectors of the same degrees of freedom then. A change of the topology, e.g., a mesh refinement, always starts from zero (see extrapolateAfterModelChange for the increment that follows it).

Both act on a prediction: a declaration of options – the *solver datalines, or an >>options block – that switches either on with extrapolation=off is refused.

The last accepted increments are checkpointed with the digest of their numbering. A step that continues from a restart checkpoint, resumed or fallen back to (see Restart), rebuilds its equation system at its first increment, and extrapolates them only if the rebuilt system numbers the degrees of freedom alike: the numbering of a meshfree model, e.g., follows its active cells, which may have changed since the checkpoint was written.

Line search and quasi-Newton fallback of the implicit solvers

Newton’s method converges quadratically close to the solution, but far from it, or where the tangent changes abruptly (e.g., material points switching between loading and unloading), a full correction can overshoot, and the iterations oscillate or diverge. Two remedies, solver options of the implicit solvers, are off by default. Under arc length control, both act on the pair of the solution and the load parameter, see Arc length control.

Line search (lineSearch). The correction \(\Delta\Delta U\) is scaled by a step length \(\alpha\): the largest residual \(\| R(\Delta U + \alpha \, \Delta\Delta U) \|_\infty\) (without the Dirichlet degrees of freedom) is evaluated at the trial step lengths lineSearchStepLengths (default 0.8, 1.0, 1.2), a parabola is fitted to these values, and \(\alpha\) minimizes the parabola on \([0.1, 1.5]\): its vertex, limited to that range, or, for a parabola that does not open upwards, the end of the range where it is smaller. A trial at which the residual is not finite fits no parabola: \(\alpha\) is then the trial step length of the smallest finite residual, and without one, the increment is cut back. Trial residuals that are equal to round-off do not tell the step lengths apart, and the correction is taken in full. Each trial costs one evaluation of the model, so the line search is done only after lineSearchAfterIterations iterations (default 5), and then in every iteration whose number is a multiple of lineSearchEveryIterations (default 2). Small trial step lengths, e.g. lineSearchStepLengths='0.15, 0.4, 0.7, 1.0', damp an iteration that cycles between two states.

Quasi-Newton fallback (fallBackToQuasiNewton). An increment whose residual grew more often than the step option maxGrowIter allows is cut back. With this option, it continues instead with the tangent of its first iteration, i.e., of the converged state at the start of the increment, or of the prediction if the increment is extrapolated. The convergence becomes linear, but a tangent that is not updated cannot switch abruptly either; maxIter still ends an increment that does not converge.

>>options, name=theSolver, lineSearch=True, lineSearchAfterIterations=2, lineSearchEveryIterations=1, fallBackToQuasiNewton=True

Convergence criteria of the implicit solvers

The implicit solvers (NIST, NISTParallel, NISTPArcLength, NID, NIDParallel) select the criterion of their Newton iterations with the solver option convergenceCriterion, e.g.:

The last two options belong to the test for a diverging Newton iteration, which holds for either criterion: an increment is abandoned, and retried smaller, once the flux residual of a field has grown more than maxGrowIter (a step option) times in it. A growth is a flux residual larger than that of the previous checked iteration, and the two options decide what else counts:

  • countFirstResidualAsGrowth (default True): the residual history of a field starts at zero, so the first checked residual of an increment is a growth already. This is EdelweissFE’s original counting; with False, counting starts with the second checked iteration.

  • countGrowthOfConvergedFields (default True): a growth counts even in an iteration in which the field is converged, and only another field keeps the iterations going. With False, such growths are ignored: the residual of a converged field fluctuates at the level of its round-off, which says nothing about divergence.

Independent of the criterion, a residual that contains a NaN ends the increment at once.

Field-wise convergence criteria for the Newton-Raphson iterations of the implicit solvers.

Two criteria are available, selected by the solver option convergenceCriterion:

legacy (default)

EdelweissFE’s own criterion. Field by field, it compares the largest flux residual \(r_{\max}\) with the spatial average flux \(\bar{q}\) of the current iteration, computed from the element fluxes only, and the largest correction \(c_{\max}\) with an absolute tolerance and with a tolerance relative to \(\Delta u_{\max}\), the largest increment of the field in the current increment. A field is converged if

\[\left( r_{\max} \leq R_a \;\text{or}\; r_{\max} \leq R \, \bar{q} \right) \quad \text{and} \quad \left( c_{\max} < C_a \;\text{or}\; c_{\max} < C \, \Delta u_{\max} \right),\]

with the tolerances of the field:

  • \(R\), the flux residual tolerance relative to the spatial average flux (fluxResidualTolerance), replaced by fluxResidualToleranceAlternative from iteration \(I\) (iterationsForAlternativeTolerance) on, where a Newton iteration that converges only slowly may stop at a looser tolerance;

  • \(R_a\), the absolute flux residual tolerance (absoluteFluxResidualTolerance): a floor for a field whose flux is so small that a relative tolerance would ask for the round-off of the residual;

  • \(C_a\), the absolute correction tolerance (fieldCorrectionTolerance);

  • \(C\), the correction tolerance relative to the largest increment (relativeFieldCorrectionTolerance); the default 0 accepts a correction by its absolute size only.

The tolerances of each field are set with *updateConfiguration, for instance

*updateConfiguration, configuration=absoluteFluxResidualTolerance
displacement=1e-10

and default to edelweissfe.config.phenomena. Three rules, set by solver options, are off by default:

  • Zero flux (zeroFluxThreshold, \(\bar{q}_0\)): a field whose spatial average flux does not exceed \(\bar{q}_0\) carries no flux its residual could be compared with, so its flux residual counts as converged. An example is a nonlocal damage field before the onset of damage.

  • Zero increment (zeroIncrementThreshold, \(\Delta u_0\)): a field whose largest increment does not exceed \(\Delta u_0\) has not moved, so there is no increment to relate its correction to; its correction counts as converged.

  • Minimum iterations (minimumIterations, \(n\)): no flux residual counts as converged before iteration \(n\), so an increment takes at least \(n\) Newton iterations. With \(n = 0\), a prediction that already satisfies the criterion is accepted as it is. The zero flux rule needs \(n \geq 1\), and refuses a smaller \(n\): before the first correction, the elements of a model at rest report no flux at all.

The scalar variables (e.g., Lagrange multipliers) are checked like a field, with the tolerances of the entry scalar variables. No element flux acts on them, so their flux residual is compared with the tolerances directly, as if their spatial average flux were one, and the zero flux rule does not apply to them: it would accept any residual of theirs for a threshold of one or more.

abaqus

The criterion of Abaqus/Standard (“Convergence criteria for nonlinear problems”, Abaqus Analysis User’s Guide), with its default parameters as printed in the .msg file of an Abaqus run without *CONTROLS. A field is converged if

\[r_{\max} \leq R_n \, \tilde{q} \quad \text{and} \quad c_{\max} \leq C_n \, \Delta u_{\max},\]

with \(R_n\) replaced by \(R_p\) from iteration \(I_p\) on. \(\Delta u_{\max}\) is the largest increment of the field in the current increment, so the correction criterion is relative. \(\tilde{q}\) is the time average flux: the spatial average flux \(\bar{q}\) averaged over all converged increments of the step in which the field carried flux, and the current iteration. The spatial average \(\bar{q}\) includes the fluxes of constraints (e.g., contact forces). Until a field has carried flux, \(\tilde{q}\) is the time average flux of the previous step or, in the first step, the initial value \(\tilde{q}^0\) (Abaqus’ “initial value of time average force”, 1e-2).

A field whose current spatial average flux is below \(\varepsilon \, \tilde{q}\) carries no flux; it is converged if \(c_{\max} \leq C_\varepsilon \, \Delta u_{\max}\). A field with \(r_{\max} \leq R_l \, \tilde{q}\) is converged irrespective of the correction (linear case).

The criterion is formulated for fields; the scalar variables are checked by the legacy criterion.

Not implemented: the estimate of the next correction from the convergence rate (Abaqus accepts an increment if it predicts a small enough correction), and the detection of inactive regions for the spatial average. Both make Abaqus’ criterion more permissive than this implementation.

Performance table of the implicit solvers

At the end of a step, and every report-performance-frequency increments if that option is set, the implicit solvers print where the step’s time went (performancetiming): one row per timed part, nested parts indented below their parent, each with its share of the step’s wall clock, its number of calls and its time per call. The table ends with the sum of the top-level rows, the wall clock since the start of the step, and the share left unaccounted, the time spent in code no timer covers. Every part of an increment is timed, so this share stays small; a large one points at work that has no row yet.

Besides the element loop and the linear solve, the rows include the parts that cost a lot on large models although no element is involved:

  • topology update: the model modifiers (e.g. AMR), then the ties and the contact catching up;

  • equation system rebuild, after a change of the mesh or of a constraint’s DOF footprint: dof manager, linear solver setup, system matrix pattern, mpc transformation build and mpc dirichlet conflict check;

  • mpc transform system matrix: condensing the slave DOFs of the multi-point constraints out of the system;

  • inertia and damping terms (NID, NIDParallel), per Newton iteration: newmark kinematics, inertia and damping forces and effective tangent;

  • reset residual and tangent, per Newton iteration;

  • accept increment, finalize increment and conservation report, per accepted increment;

  • output, per output increment: field output and one row per output manager, under the name of its *output line.

The timers start from zero together with the step’s wall clock, so the rows and the wall clock of a step’s table cover the same time, whatever ran before the step. A resumed run (*restart, readFrom=...) whose checkpoint replays a topology history prints that replay in a table of its own (top-level AMR rows), before the step’s table.

NED - Nonlinear Explicit Dynamic

The nonlinear explicit dynamic solver.

An increment solves no equation system. Second-order fields are advanced by central differences (a leapfrog, with the velocity staggered half an increment behind the displacement), first-order fields – a nonlocal damage field, for instance – by forward Euler, and both divide by a lumped mass, so the cost of an increment is one element pass plus vector arithmetic. There is no linear solver, no Newton loop, and no cutback: the time increment is set by stability, not by convergence, so a material that fails to integrate at the stable step is reported as an error rather than answered with a smaller step.

Inertia and damping. An element reports two diagonals: the coefficient of each field’s second time derivative (its inertia) and of its first (its damping). The integrator divides by the one and relaxes with the other, and which scheme a field gets is read off them – an inertia means central differences, a damping alone means forward Euler. The deck declares no field ordering, because an inertia is exactly what a central-difference update divides by. At zero damping the update is bit-identical to the undamped one.

The diagnostics need one thing more, and it is about units: which entries of the inertia diagonal may be summed. That belongs to the FIELD rather than to a deck, and is recorded in edelweissfe.config.phenomena as a mass, a rotational inertia, or neither. Linear momentum sums the first kind, the energy balance the first two; conservation across a topology change is checked per field regardless.

The case that forces it: a first-order field’s forward-Euler limit falls off with the SQUARE of the element size, so on a refined mesh it, not the mechanical field, bounds the increment. Giving it an inertia makes it second order – a damped wave equation, limit linear in h – with its old coefficient keeping its value and becoming the damping. Marmot supplies one through the nonlocal micro inertia element property; that inertia is a time squared, so 0.5 m_k rate^2 is a volume rather than an energy and the field is registered as carrying a non-mechanical inertia, which keeps it out of both balances.

first-order-fields, second-order-fields, first-order-scheme and second-order-scheme are removed rather than deprecated: a deck carrying any of them now fails with Invalid option, and deleting those lines is the whole of the migration.

The stable increment is computed once per mesh from the element wave speeds and scaled by courant-number. It is recomputed whenever the mesh changes and deliberately not recomputed when it has not: as a material softens the true limit only grows, so reusing it is the conservative direction, and re-deriving it costs a full element pass.

Three cadences, all in increments. output-frequency is how often progress is logged and field outputs are finalized (a divisor, so it must be at least 1). topology-check-frequency is how often model modifiers may change the mesh mid-run, and must be a multiple of output-frequency because a marker reads the last finalized output; 0 runs the topology update only once, before the increment loop. contact-update-frequency is how often constraints whose connectivity is the outcome of a search re-run it; 0 disables that. The reasoning behind the latter two, and what they cost in accuracy, is documented under Adaptive refinement: error estimation and marking and Contact mechanics: theory respectively.

Constraints. Multi-point constraints are enforced by folding a slave’s mass and force onto its masters (row-sum, mass-conserving) and slaving it kinematically, which leaves the critical time step untouched. Other constraints – contact above all – are evaluated through computeKernelsExplicit(), which asks for forces and no tangent, since a tangent assembled here would enter nothing. A constraint that can act only through its tangent contributes nothing to an explicit increment and is refused at validation rather than silently ignored.

Energy balance. Every reporting increment prints the external work accumulated at prescribed degrees of freedom, the kinetic energy, the internal (strain) energy, and what remains unaccounted. Its purpose is one check that nothing else performs: kinetic energy cannot exceed external work, because the terms omitted from the balance are all non-negative, so a violation means energy is appearing from nowhere and the time step is above the true stability limit – which the critical time step does not see in full, as it never sees contact penalty stiffness, and sees the nonlocal field only where that field carries a non-mechanical inertia. Such a field’s own 0.5 m_k rate^2 is reported on a separate line and kept out of the balance: with a coefficient in seconds squared it has the units of a volume, not of an energy.

Two honest limits, both of which the solver states in the log rather than leaving to be discovered. The external work accumulates only at prescribed degrees of freedom, so a model driven by body forces, node forces, a distributed load or an initial velocity has none, and the check cannot fire; and the internal energy is whatever the materials publish as a strain energy, which not every material does. When either is identically zero – or the external work is negative, a structure returning work at its boundary – the balance is not usable as a quasi-static criterion, and the honest substitute is to integrate a reaction force against its prescribed displacement, both of which are available as saveHistory field outputs.

Diagnostics across a topology change. Because the lumped mass is the operator an increment divides by, a refinement’s effect on it is reported: total mass, per-component linear momentum and kinetic energy before and after, plus the relative mass drift accumulated over every such change, so that many individually-tolerable changes cannot silently add up to a meaningful one. The smallest coefficient the increment divides by is reported alongside – an inertia at a second-order degree of freedom, a damping at a first-order one – since that is what bounds the step.

Restart. A resumed run must not repeat the half-step that starts a leapfrog: the velocity in the checkpoint already carries the half-increment offset, so applying the startup again would apply one half-impulse too few. The solver therefore takes the previous time increment from the restart state rather than synthesising it, and the velocity field is checkpointed in its own right – an implicit solver reconstructs everything it needs from the displacement, a central-difference scheme does not.

Report what a topology change did to the quantities that ought to survive it.

Refinement interpolates the velocity onto new nodes and re-lumps every per-element scalar property, and the three invariants behave differently under that:

  • Every field’s own lumped total is conserved exactly, by the same geometric identity regardless of what that field’s coefficient physically is: the children of a refined element tile it and carry the same value. Checked per FIELD, not per family, via ConservationCheck – summing across fields first, even ones that agree on units, would let a violation in a numerically small field hide inside a numerically large one. Violating any single field’s total raises.

  • Linear momentum is conserved exactly for a spatially uniform velocity field, because the shape functions are a partition of unity and the child masses sum to the parent’s. For a general field the discrepancy is second order in the velocity gradient across the parent: discretisation error, not a defect. Reported, not enforced. Restricted to the fields whose inertia is a mass, per carriesLinearMomentum(): a viscosity or a non-mechanical inertia has no associated momentum, and a rotational inertia has an angular one that must not be added to a linear one. Across those fields the sum IS legitimate, because a real total system momentum is exactly the sum of its parts’ momenta.

  • Kinetic energy is not conserved by interpolation plus re-lumping, and it is the most sensitive of the three, being quadratic in the interpolation error. Reported as a relative jump; more than roughly a percent is a reason to look at the transfer rather than to believe the physics. Restricted to the fields whose 0.5*m*v**2 is an energy – the mass-carrying ones and the rotational ones, a wider set than momentum admits – and reason, and summed across them for the same reason momentum is.

Omitted – as in every deck that predates them – they assert nothing at all.

Rebuilding the equation system during a step

An explicit analysis with contact rebuilds its equation system while it runs: a contact search re-assigns which nodes a constraint couples, which changes that constraint’s degree-of-freedom footprint, and everything sized by the footprints has to follow.

Such a change is much narrower than it looks. It touches no node, no field, no scalar variable and no element, so the degree-of-freedom numbering and every element’s indices stay exactly as they were – and with them the lumped inertia, its inverse, the mass-proportional damping rate and the multi-point-constraint transformation, none of which is a function of the constraints’ footprints. The solver therefore re-locates the constraints alone (refreshConstraintIndices()) and keeps those operators, rather than constructing a new DofManager and assembling them again over every element.

That shortcut is only valid while everything the operators are a function of is unchanged, so it is taken only after checking the element set, the multi-point constraints, the node count and the scalar variables against what was recorded when they were last assembled, and only when no step action changes a material property mid-step. Anything that does not match falls back to a full build. A topology change – a mesh refinement – is not a connectivity change and never takes this path at all: it builds the system from scratch.

Work per increment outside the elements

An explicit increment is cheap, so the work around the element loop counts. Second-order degrees of freedom are updated by the central difference with mass-proportional damping, first-order ones by forward Euler. The damping rate and a second-order mask are formed once per equation system, so the update runs on whole vectors instead of indexed subsets, and gives the same result to the bit.
