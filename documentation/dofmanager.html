Degree of Freedom (DOF) Manager and Numerics

The edelweissfe.numerics package provides core data structures and managers for global equation systems in EdelweissFE.

The DOF manager numbers the degrees of freedom: every node field, scalar variable and entity gets its indices in the global DOF vector. It knows nothing about the system matrix. How the blocks of the entities – each given in the entity’s own numbering by SystemMatrixContributorBase – become the global matrix is the business of the system matrix assembly, see System matrix assembly.

DofManager

This module contains important classes for describing the global equation system by means of a sparse system.

class edelweissfe.numerics.dofmanager.DofManager(nodeFields, scalarVariables=None, elements=None, constraints=None, nodeSets=None, initializeAccumulatedNodalFluxesFieldwise=True)[source]

Bases: object

The DofManager coordinates the global equation system structure.

Specifically, DofManager:

  • Analyzes the simulation domain (nodes, scalar variables, elements, constraints, and node sets).

  • Collects and assigns global Degree-of-Freedom (DOF) indices for node fields and scalar variables.

  • Manages entity-to-index mappings for fast scatter/gather operations: the global DOF list of every element and constraint, from which a system matrix assembly derives where each block goes.

  • Calculates accumulated elemental/constraint fluxes fieldwise for convergence tests.

  • Constructs domain-aware DofVector and ScatterDofVector instances.

Parameters:

  • nodeFields (list of NodeField) – The list of NodeFields to be represented in the DofVector structure.

  • scalarVariables (list of ScalarVariable, optional) – The list of ScalarVariables to be represented in the DofVector structure.

  • elements (list of BaseNodeCouplingEntity, optional) – The list of Elements for which DOF index mappings will be created.

  • constraints (list of BaseNodeCouplingEntity, optional) – The list of Constraints for which DOF index mappings will be created.

  • nodeSets (list of NodeSet, optional) – The list of NodeSets for which DOF index mappings will be created.

  • initializeAccumulatedNodalFluxesFieldwise (bool, optional) – Whether to compute accumulated nodal fluxes fieldwise during construction. Default is True.

Attributes:
dofNumberingDigest

A digest, a hexadecimal string, of what decides the index of every degree of freedom: for every field, its name, its dimension, its slice in the DofVector and the labels of its nodes in the order they are numbered; and the names of the scalar variables, which follow, in the order they are numbered. Two equation systems with the same digest give every degree of freedom the same index, so a DofVector of one is a DofVector of the other – e.g., before and after a rebuild caused by a contact search, which changes the coupling of the degrees of freedom but not their numbering. The scalar variables are named, not counted: they are those of the constraints switched on, which a constraint may change within a step (switched from outside, or by itself), so that two systems with as many scalar variables may number different ones.

The digest names the nodes by their labels, so it is the same in every run of a model: a restart checkpoint holds it together with the vectors it numbers. Computed at the first request; the numbering of a DofManager does not change.

indexToHostObjectMapping

The node of every index of a field variable in the DofVector, built on first use: only the report of the largest residual of an implicit solver reads it (through getNodeForIndexInDofVector()), while building it costs a pass over every degree of freedom, which a DOF manager that is never asked – one of the many an explicit solver builds over a run, say – does not pay.

locateFieldOnNodeSet(field, nodeSet)[source]

Where the degrees of freedom of a field on the nodes of a node set lie in the DofVector, e.g. those a Dirichlet boundary condition prescribes, or those a node force acts on.

Only the nodes whose field is part of this equation system count. In a finite element model, these are all nodes of the set that carry the field. A model whose equation system covers a part of its nodes only – the active domain of a material point method model, the nodes in the support of an RKPM model’s particles – leaves the other nodes of a set out. Values given per node of the set (the prescribed values of a boundary condition, the forces of a node force) are then selected by the positions of the remaining nodes in the set, which this method returns along with the indices.

The node sets given at construction are located up front, any other one at its first request.

Parameters:

  • field (str) – The name of the field, one of this equation system.

  • nodeSet (NodeSet) – The node set.

Returns:

  • The indices of the degrees of freedom in the DofVector, node after node in the order of the set, on each node the components of the field.

  • The positions of these nodes in the set: the rows of an array that holds one row per node of the set.

Return type:

tuple[np.ndarray, np.ndarray]

refreshConstraintIndices(constraints)[source]

Re-locate the constraints’ degrees of freedom after their connectivity changed.

A contact search re-assigns which nodes a constraint couples. That changes the constraints’ DOF footprints and nothing else: no node, field, scalar variable or element is touched, so the DOF numbering and every element’s indices stay valid, and only the constraint-derived bookkeeping has to be recomputed – by the same methods, in the same order, as the constructor computed it. That is a small fraction of what constructing a DofManager for the same model costs, and it is the whole reason this method exists rather than a second constructor call.

This does NOT re-derive the degree-of-freedom layout itself: the node fields and the scalar variables keep the indices they were given. A change that moves those – a mesh refinement, a constraint gaining a scalar variable of its own – is not a connectivity change and needs a new DofManager.

The merged entity mapping is rebuilt as a new dict object on purpose: consumers cache plans keyed on its identity (the scatter template, the element loop’s gather plan), and a mapping mutated in place would leave those plans silently stale.

Parameters:

constraints (list) – The constraints, with their current connectivity.

class edelweissfe.numerics.dofvector.DofVector(nDof, entitiesInDofVector=None)[source]

Bases: ndarray

Represents a Degree-of-Freedom (DOF) vector with entity-aware indexing.

A DofVector is a 1D NumPy array subclass augmented with metadata mapping simulation entities (such as elements, constraints, or node sets) to their respective DOF indices. This enables direct indexing and assignment using entity objects as keys.

Parameters:

  • nDof (int) – The total number of degrees of freedom (length of the vector).

  • entitiesInDofVector (dict, optional) – A dictionary mapping entities (or entity keys) to their index arrays or slices in the DofVector.

The same buffer seen as a plain numpy.ndarray, built once and cached.

Indexing through this bypasses the subclass wrapping that dominates hot-path access – see __getitem__(). It aliases this vector rather than copying it, so writes through it are writes to this vector. Callers that index a DofVector repeatedly in a loop should take this once outside the loop instead of calling view(np.ndarray) themselves.

The entities that contribute a block to the system matrix – elements, constraints, and whatever else couples nodes – and the layout of that block.

class edelweissfe.numerics.systemmatrixcontributor.SystemMatrixContributorBase(nDof)[source]

Bases: object

Base class for the entities that contribute a block to the system matrix.

The block couples the entity’s degrees of freedom with each other. By default it couples all of them: the block is the dense nDof x nDof matrix, stored column-major. An entity that couples only some of its degrees of freedom (a contact constraint, which couples every slave node with the master side but not the slave nodes with each other) lists the local row and column of each value of its block: it overrides localEntriesOfBlock(), and that is all it does to declare the layout of its block (couplesAllItsDofs follows from it). The number of values of a block is always the length of that list (countEntriesOfBlock()).

The layout is declared once, by the override: a subclass that declares couplesAllItsDofs itself is refused when it is defined, as a second declaration could contradict the first. An extension type, which cannot inherit this class (the Marmot elements, for one), declares both itself: a dense block, whose localEntriesOfBlock() is denseBlockLocalEntries().

property couplesAllItsDofs: bool

Whether the entity’s block couples every one of its degrees of freedom with every other one.

True (the default, every element) means the block is the dense nDof x nDof matrix, stored column-major. False means the entity lists the entries of its block itself, by overriding localEntriesOfBlock(), and its block is the list of their values, in that order. It is False exactly for the entities that override it.

The layout is never guessed from the number of entries, which cannot tell: a sparse pattern can happen to have exactly nDof**2 entries. A rigid body contact with a single slave node in 3D couples the six degrees of freedom of the reference point with each other, the three of the node with each other, and the two groups both ways: 36 + 9 + 18 + 18 = 81 = 9², yet its entries are ordered block by block, not column by column.

Call work(s) for consecutive slices s that together cover range(length), on the persistent thread pool, and return what the calls returned, in the order of the slices.

Meant for the simple array operations on arrays as long as the system matrix – zeroing it, adding a scaled mass matrix to it (addMatrix()) – which numpy runs on a single thread, and which on a large model take seconds per Newton iteration that way. Every call works on its own part of the arrays, so the result is bitwise the one of the same operation on the whole array. Call work(worker, chunk) for consecutive chunks of items, each chunk on a fixed worker thread, and return what the calls returned, in the order of the chunks.

For an entity loop whose workers write through memory of their own, which no other call may use at the same time – each worker its own scratch array for the blocks of the system matrix (see blocksOfWorker()). Unlike mapChunksInParallel(), which hands each chunk to whichever thread is free, the chunks are dealt out to the workers in turn: worker w handles chunks w, w + numberOfWorkers, …, in this order, so every worker meets the same entities in every run. Report how many threads will be used, and warn if the process cannot actually use them.

A pool of numThreads workers only runs on numThreads cores if the process is permitted to use that many, and OMP_PROC_BIND/OMP_PLACES are the common reason for it not to be: they make the OpenMP runtime pin the thread that loads it to a single place, and every thread started afterwards – the pool’s workers included – inherits that one-core mask.
