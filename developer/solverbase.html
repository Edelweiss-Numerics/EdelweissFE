The solver base class

Every nonlinear solver derives from NonlinearSolverBase. It runs the topology update, builds and renews the discrete system through the one path of How a change selects the path, and declares the two hooks, onNewNumbering and onNewLocations, that every solver implements for what it holds. It also assembles the loads and the constraints (The residual and the tangent), and checks convergence. A solver that holds more than the base class extends forgetDiscreteSystem.

static collectLoads(stepActions)[source]

The loads among a step’s actions: every action that is a LoadBase, whatever step action module it is defined in, so that a new kind of load needs no change to any solver.

They come in the order in which their contributions are summed, module by module: the node forces, the distributed loads and the body forces first, then the loads of any other module, by the name of the module; within a module, in the order of their definition. A fixed order makes the residual the same sum in every run.

Parameters:

stepActions (dict) – The step actions, by module.

Returns:

The loads.

Return type:

list[LoadBase]

applyDirichletToResidual(timeStep, R, dirichlets)[source]

Impose the Dirichlet BCs on the residual.

For every constrained DOF we overwrite its residual entry with the value we want the linear solve to return for that DOF’s increment. Together with applyDirichletToStiffness() (which replaces the DOF’s row of K by the identity and eliminates its column into R), the linearized system K ddU = R then reproduces exactly that increment for the DOF.

Parameters:

  • timeStep (TimeStep) – The current time step.

  • R (DofVector) – The residual vector of the global discrete system to be modified.

  • dirichlets (list[StepActionBase]) – The list of dirichlet boundary conditions.

Returns:

The modified residual vector.

DofVector

applyOptionsOverride(fieldValues)[source]

Apply a partial override of this solver’s own schema fields onto self.options.

The counterpart, on the solver side, of the name-based >>options override mechanism (stepactions/options.py): once that mechanism has resolved an >>options, name=X, ... block to this solver instance and validated the present keys against type(self).schema via coercePresentOptions(), it calls this method with the result to actually apply them.

fieldValues is keyed by schema field name (e.g. rungeKuttaStages), while self.options – read throughout a step – is keyed by the option’s .inp-facing spelling (e.g. "runge-kutta-stages"), which are not always the same (a hyphenated name cannot be a Python identifier). The schema’s optionName metadata is the one place that mapping is recorded, so it is consulted here rather than duplicated.

Parameters:

fieldValues (dict) – Maps schema field name to its new, already-coerced value.

Return type:

None

assembleConstraintForces(constraints, U_np, dU, P, timeStep)[source]

Evaluate the constraints of the discrete system and add their residual contributions to the given vector.

The explicit counterpart of assembleConstraints(), with the same sign: a constraint adds the negative of the force it exerts on the nodes, like an element its internal force, see The residual and the tangent.

No tangent is requested. An explicit increment solves no linear system, so a constraint’s stiffness enters nothing, and computeKernelsExplicit() is the entry point that evaluates the constraint forces directly without assembling a tangent. A constraint that could act only through its tangent would contribute nothing here; an explicit solver refuses it in its validateModelCapabilities.

The force buffer and the DOF indices of each constraint are kept in _constraintForcePlans (by constraint) and reused in every increment. They hold for the indices of the constraint they were made for: whenever the locations locate the constraint anew – a rebuilt discrete system, or one with new locations –, the constraint has indices of its own, its plan is made anew, and the constraint is told so (prepareExplicitEvaluation()).

Parameters:

  • constraints (list) – The constraints of the discrete system (constraints).

  • U_np (DofVector) – The current solution vector.

  • dU (DofVector) – The current solution increment.

  • P (DofVector) – The residual contribution vector to be augmented.

  • timeStep (TimeStep) – The current time step.

Returns:

The augmented residual contribution vector.

Return type:

DofVector

locateConstrainedDofs(dirichlets)[source]

Determine, up front, which global DOFs each Dirichlet BC constrains.

Called at the start of every increment, before its iterations: the numbering of the degrees of freedom may have changed since the last increment – a rebuild of the discrete system after a change of the mesh or of the coupling, or a new active domain of a meshfree model, which locates a node set anew. The result is cached on each BC as constrainedDofIndices, together with the positions of their nodes in the BC’s node set (constrainedNodePositions), so that the Newton loop can address the constrained DOFs directly, instead of recomputing the mapping on every residual update and every stiffness modification.

Parameters:

dirichlets (list[StepActionBase]) – The list of dirichlet boundary conditions active in this step.

updateDiscreteSystem(model, change)[source]

Bring the discrete system up to date with what changed: the one way a solver builds its discrete system, from the first to the last increment.

  • No discrete system yet, or a change of the numbering or of the mesh (NUMBERING, MESH): the model builds a new one (buildDiscreteSystem()), then onNewNumbering() and onNewLocations() follow. The old one is dropped before (forgetDiscreteSystem()): never both at once.

  • A change of the locations (LOCATIONS): the same numbering, new locations (withNewLocations()); only onNewLocations() follows, so that nothing sized by the numbering is touched.

  • Else nothing.

The change is the one updateTopologyAndConnectivity() reports: the model classifies what its entities report, and the topology update adds a change of the mesh. The solver never tests whether an entity changed.

Parameters:

  • model (FEModel) – The model tree.

  • change (Change) – What changed since the discrete system was built.

updateRigidBodies(model, timeStep)[source]

Refresh the kinematics of all rigid bodies in the model after a converged increment.

A rigid body’s surface (visualization) nodes are not degrees of freedom of their own; they are fully determined by the rigid body’s reference point. This propagates the just-converged reference-point pose onto those surface nodes so that output managers write the transient geometry of the moving body and any consumer relying on the surface nodes’ coordinates (e.g. the fast-path AABB of getAABB()) sees the current configuration.

Every nonlinear solver must call this once per converged increment, in acceptIncrement().

Parameters:

  • model (FEModel) – The model tree.

  • timeStep (TimeStep) – The converged time step.

updateTopologyAndConnectivity(model, step, offerModelModifiers=True)[source]

Run the topology update, then let every mesh-dependent consumer catch up on it, and say what changed.

Two phases. First, the model modifiers plan and apply to a fixed point inside one topology window (update()). Second, the pure readers of the settled model catch up, once, on the net change: the tie and contact surfaces, then the connectivity, which the model brings up to date itself (updateConnectivity(); the constraints of a finite element model, e.g. a contact search). They may not create or delete elements: the topology window is closed by then, so an attempt raises.

One Change comes out of it, the same for every solver:

  • MESH if the model modifiers changed the mesh, or if a mesh-dependent consumer caught up (e.g. a tie or contact surface rebuilt on a mesh that changed in a way that concerns it). A consumer refreshes only when the topology version advanced, i.e. when nodes or elements did change, so its catching up is a change of the mesh whoever made it, and its changed records (e.g. the multi-point constraints of a tie) are sized by that mesh.

  • Otherwise the model’s answer.

Parameters:

  • model (FEModel) – The model tree.

  • step – The step being solved.

  • offerModelModifiers (bool) – False when an increment is retried after a cutback. The model modifiers decide once per converged state: the retry starts from the state they already decided on.

Returns:

What changed; the solver decides from it how much of its discrete system to renew.

Return type:

Change
