Linear solvers: Python API

The classes and functions of the linear solvers. How to choose a linear solver is on Linear solvers, how to compose one on Composing a linear solver, the arguments and data lines at a glance on Composed linear solvers: reference.

The types and the configuration

The types of linear solver: what linsolver=<type> (and, with its data lines, *linearSolver, type=<type>) names.

Every type is a composed solver behind the one adapter, ComposedLinearSolver: a type is the schema of its data lines and the tree they define (LinearSolverType.tree()). A direct solver is a tree of one leaf, type=pardiso is DirectSolver("pardiso"). So what the adapter does – the verbosity, the dumps, the “linear solve” column – works the same for every type, and the data lines of LinearSolverSchema are those of every type.

Return a linear solver of the type linsolverName, configured with options.

Parameters:

  • linsolverName (str) – The type of the linear solver, case-insensitively (e.g. "pardiso", "blockamg", "custom"; registry category linsolver, see edelweissfe.linsolve.types).

  • options (dict) – The data lines of that type by name, e.g. {"reuseSymbolicFactorization": True} or {"script": "solver.py"}; {} for its defaults.

Returns:

A callable (A, b) -> x solving A x = b.

Return type:

LinearSolver

Raises:

  • edelweissfe.config.registry.RegistryLookupError – If no linear solver is registered under linsolverName.

  • ValueError – If options names an option the type does not have, or a value it cannot take.

  • ImportError – If the requested solver’s optional backend is not available in this installation (see getDefaultLinSolver(), which relies on it).

The components

The building block of a composed linear solver: Preconditioner, an approximate inverse \(M^{-1}\) of a matrix \(A\), and what is handed to it – the SetUpContext of its (sub-)problem and the MatrixChange since its last set-up.

A composed solver is a tree of preconditioners. Each one solves its part of the problem and hands a smaller problem to its children: a Krylov solver calls its preconditioner once per iteration, a Schur complement solves the condensed dofs exactly and hands the remaining ones to its child, a diagonal scaling multiplies by \(D\) before and after its child. A Krylov solver is itself a preconditioner – an approximate inverse of \(A\) – so solvers nest like any other component.

A component implements what makes it what it is, in protected hooks:

  • Preconditioner._setUp() builds it for a matrix (and its children for their sub-problems);

  • Preconditioner._forget() drops what it built, and so declares what that is (the constructor calls it);

  • Preconditioner._update() takes a changed matrix and decides what to keep (by default: set up again);

  • Preconditioner._apply() applies it, \(z = M^{-1} r\) – the formula of the textbook;

  • Preconditioner.children() names its children, if it has any (the tree is walked through it);

  • Preconditioner.describe() says what it is, for the views (views).

It is used through the public methods of the base class, setUp(), update() and __call__() (a template method each): they record the call and its time in the component’s Statistics and call the hook. So a component’s _apply holds nothing but its formula, and a hook that calls another hook of its own component (a Krylov solver’s _setUp is its _update for a first matrix) counts as one call.

A component builds only through setUp(), also when an update decides to rebuild (it calls self.setUp). setUp() first forgets what was built before (forget(): the _forget() of the component and of its children), so that the old and the new hierarchies, factorizations and matrices, gigabytes for a large model, are never held at once. An update that does not rebuild keeps what was built, and what is reused on purpose is never forgotten: the selection of a Schur complement’s condensed dofs, a symbolic factorization, the statistics. A component with nothing built builds at its next update, whatever the update says.

Symmetric diagonal scaling: DiagonalScaling.

\[M^{-1} = D \, \hat M^{-1} D, \qquad \hat M \text{ built on } \hat A = D A D, \qquad D = \operatorname{diag}(\lvert a_{ii} \rvert^{-1/2})\]

Every diagonal entry of \(\hat A\) is \(\pm 1\). The fields of a coupled system have very different units – the rows of a displacement field carry stiffnesses, those of a nonlocal damage field entries of order one – and AMG and a block Gauss–Seidel sweep compare matrix entries with each other (the strength-of-connection test \(\lvert a_{ij} \rvert \geq \theta \sqrt{\lvert a_{ii} a_{jj} \rvert}\), the couplings between fields, the Chebyshev eigenvalue bounds). \(D = \operatorname{diag}(\lvert a_{ii} \rvert^{-1/2})\) of a matrix, from its absoluteDiagonal \(\lvert a_{ii} \rvert\), for DiagonalScaling.

A zero diagonal entry cannot be scaled: \(1/\sqrt{0}\) is infinite, which would poison \(\hat A\) with non-finite values before the preconditioner build, and the failure would surface much later as a NaN correction (i.e. as a diverged solution, which reads like a physics problem rather than an unsupported system). edelweissfe.linsolve.composition.amg.droppedSmallEntries(A, dropTolerance, lumpDroppedEntries=False)[source]

The filtered matrix \(\tilde A\) of A that a preconditioner is built on: the off-diagonal entries that fail the relative drop test (isSignificant()) at \(\tau\) = dropTolerance dropped. The diagonal is always kept, so no row is emptied. Shared by AMG and TwoLevel.

Why: some operators (e.g. of RKPM) store many entries per row whose median off-diagonal is orders of magnitude below the diagonal – numerically far sparser than structurally. Smoothed aggregation then weighs every one of them per row, and the Galerkin products carry them to every coarse level. Only the preconditioner is built on \(\tilde A\); the Krylov solve still applies \(A\), so the converged solution is that of \(A\), and only the number of iterations to reach it changes. The criterion is scale-invariant and symmetric in \((i, j)\): a symmetric matrix stays symmetric, as smoothed aggregation and the Chebyshev smoother assume.

edelweissfe.linsolve.composition.amg.NEAR_NULLSPACES = ('rigidBodyModes', 'translations', None)

The near null-spaces AMG builds its hierarchy from, see backendOf().

A two-level cycle with a coarse space of its own: TwoLevel.

One cycle, for \(z \approx A^{-1} r\) with a prolongation \(P\) from the coarse space:

\[\begin{split}z &\leftarrow S^{\nu_1}(0, r) && \text{pre-smoothing (Chebyshev)} \\ z &\leftarrow z + P \, A_c^{-1} P^T (r - A z) && \text{coarse correction}, \quad A_c = P^T A P \\ z &\leftarrow S^{\nu_2}(z, r) && \text{post-smoothing}\end{split}\]

with \(A_c^{-1}\) approximated. The coarse space decides what the cycle can correct:

  • RigidBodyModesPerAggregate: all rigid-body modes of each aggregate of nodes (3 translations and 3 rotations in 3D), where an AMG hierarchy on node-wise 3x3 blocks takes the translations alone; \(A_c^{-1}\) is one V-cycle of an AMG hierarchy;

  • CornerNodeInterpolation: the linear interpolant of a quadratic field from its corner nodes (P1); \(A_c^{-1}\) is a component of its own on the corner-node field, by default DiagonalScaling(AMG()). For a 3D displacement field, DiagonalScaling(TwoLevel(coarseSpace=RigidBodyModesPerAggregate())) makes three levels: quadratic, linear, rigid-body modes of aggregates. On such a field the fine level smooths with the smoother of the corner-node two-level cycle, a Chebyshev polynomial of degree 8 instead of 16 (defaultCornerNodeTwoLevelTree()), and the blockamg preset gives the coarse level the same.

Why “two-level”: the component is the fine level and one coarse correction, and its coarse problem is solved inexactly. The coarse space need not be a coarser mesh. With RigidBodyModesPerAggregate it is spanned by aggregates of nodes, and the whole cycle is smoothed aggregation with all rigid-body modes on every level, the method Trilinos ML and MueLu use for elasticity (Vaněk, Mandel and Brezina, Computing 56, 1996). The first coarse level is built here, on the node-wise blocks of the fine level, with the modes scaled by the diagonal scaling and zero on the Dirichlet rows. The levels below are built by AMGCL, which takes the coefficients of the modes in the coarse space as its near null-space. prolongation="tentative" makes the first level plain aggregation. With CornerNodeInterpolation the coarse level is a coarser grid, the corner nodes (p-multigrid): a field of its own, which its coarse component solves like any field (cornernodetwolevelcycle).

The cycle runs in C++ (rigidbodymodestwolevelcycle, cornernodetwolevelcycle; the coarse component of CornerNodeInterpolation is called back once per cycle). Its steps, written out in Python, are Multiplicative([smoother, CoarseCorrection(P, coarseSolve), smoother]) (combinators). Both ways are kept on purpose: this one is faster per application, the spelled-out one shows the steps and takes any smoother or coarse space. Why, and what would end the exception: the “two-level cycle: two ways” section of doc/source/analysis/composedlinsolvers.rst.

Description

Condensing hard dofs exactly: SchurComplement, a block LU factorization around a child, and the condensation it is built from, SchurComplementCondensation.

Some dofs make a system hard for AMG: the dofs of embedded bars tied to their host elements by bond springs (\(u_{bar} \approx \sum_i N_i u_i\), which an aggregation coarse space cannot represent), or the dofs of a softening zone. We call these dofs \(b\) (the condensed dofs: “bars”) and all others \(k\) (the kept, or remaining, dofs). Ordered this way, the system reads

\[\begin{split}\begin{bmatrix} A_{bb} & A_{bk} \\ A_{kb} & A_{kk} \end{bmatrix} \begin{bmatrix} x_b \\ x_k \end{bmatrix} = \begin{bmatrix} r_b \\ r_k \end{bmatrix}.\end{split}\]

The block \(A_{bb}\) is factorized exactly (a direct solver). Eliminating \(x_b\) leaves the remaining dofs with the Schur complement \(S = A_{kk} - A_{kb} A_{bb}^{-1} A_{bk}\) – for bars, the concrete stiffened by the bars as seen through their bond – on which the child of SchurComplement is built (e.g. a field-split AMG). Gaussian elimination by blocks is the block LU factorization of \(A\), and its inverse is a preconditioner of the outer Krylov solve:

\[y_b = A_{bb}^{-1} r_b, \quad z_k = M_{\tilde S}^{-1} (r_k - A_{kb} y_b), \quad z_b = A_{bb}^{-1} (r_b - A_{bk} z_k),\]

with \(M_{\tilde S}^{-1}\) the child (schurComplementSolve) on an approximation \(\tilde S\) of \(S\). With \(\tilde S = S\) and an exact sweep it is \(A^{-1}\).

It solves with \(A_{bb}\) twice. The default (blockFactors = "upper") inverts only the block upper triangular factor \(U = \begin{bmatrix} A_{bb} & A_{bk} \\ 0 & S \end{bmatrix}\) of \(A = \begin{bmatrix} I & 0 \\ A_{kb} A_{bb}^{-1} & I \end{bmatrix} U\), with one solve:

\[z_k = M_{\tilde S}^{-1} r_k, \quad z_b = A_{bb}^{-1} (r_b - A_{bk} z_k):\]

the remaining dofs first, then the condensed ones follow them (for bars: the bars follow the concrete). Its last step solves the rows of \(b\) exactly, so after the first outer iteration the residual of these rows is zero, and the outer Krylov solve iterates on the rows of \(k\) alone, with the operator \(S \tilde S^{-1}\): the same operator as with the full block LU factorization. With exact \(S\), GMRES converges in two iterations instead of one; with \(\tilde S\) and AMG, the outer iterations hardly grow, and every one saves a solve with \(A_{bb}\).

\(S\) is dense wherever \(A_{bb}^{-1}\) is, e.g. along a whole bar. Its entries decay quickly away from the diagonal, though (a bar on its bond is a beam on an elastic foundation: a load is felt only a few host elements away), so \(\tilde S\) keeps only the significant ones:

  • a banded component of \(A_{bb}\) (a bar, ordered along the bar) is cut into overlapping windows of nodes along it; for the dofs of a window’s core, \(A_{bb}^{-1}\) is replaced by the inverse of the window’s block (restricted additive Schwarz); a short component is a single, exact window,

  • a component that is not banded (a zone of a 2D or 3D mesh, e.g. a softening zone) gets its exact correction from a factorization of its own block, in batches of right-hand sides,

  • entries \(|\tilde S_{ij}| < \tau \sqrt{|\tilde S_{ii} \tilde S_{jj}|}\) are dropped (dropTolerance).

Which dofs are condensed is decided by markers, the same ones that mark elements for adaptive refinement (edelweissfe.adaptivity.marking): \(b\) holds all dofs of the interior nodes of the marked elements, i.e., of the nodes that have at least one element, all of them marked:

bar node:   bar, bond                -> all marked -> condensed
host node:  bond, concrete, concrete -> not all    -> kept

For embedded bars, mark the bar and the bond elements. For a softening zone, mark the elements of a perElement fieldOutput above a threshold, with a halo so that the zone’s own nodes become interior. Only the dofs of nodes can be condensed, and always all fields of a node together.

They are the vocabulary of Schwarz methods, and methods which look unrelated share their structure:

  • a correction on one field is \(R_i^T M_i^{-1} R_i\), with \(R_i\) the restriction to the field’s dofs and \(M_i^{-1}\) a preconditioner of its diagonal block \(A_{ii} = R_i A R_i^T\): OnField(name, M_i);

  • block Gauss–Seidel over the fields is their multiplicative combination, Multiplicative([OnField("displacement", M_u), OnField("nonlocal damage", M_d)]), and block Jacobi their additive one, Additive([...]); a symmetric sweep visits the fields forward and back, see gaussSeidelOrder();

  • a two-level cycle is a multiplicative combination of a smoother, a coarse correction and the smoother again, Multiplicative([Jacobi(), CoarseCorrection(P, coarseSolve), Jacobi()]).

This is also the fast way. A combination asks each correction which field it acts on (fieldIndex), and computes the residual of a correction on field \(i\) only on that field’s rows, from the fields corrected so far:

\[r_i - \sum_{j:\, z_j \neq 0} A_{ij} z_j\]

with the blocks \(A_{ij}\) formed once per matrix in one threaded pass (fieldSplit()) and read only as products. A correction on all dofs gets the residual of all fields.

class edelweissfe.linsolve.composition.combinators.CoarseCorrection(prolongation, coarseSolve)[source]

The coarse-grid correction \(z = P A_c^{-1} P^T r\) with the Galerkin coarse operator \(A_c = P^T A P\). With an exact coarse solve, \(P A_c^{-1} P^T A\) is the \(A\)-orthogonal projection onto the range of \(P\).

\(P\) is built at a set-up and kept until the next rebuild (see requiresRebuild). On a change of the values alone it recomputes \(A_c = P^T A P\) and hands it to the coarse solve as an update, which keeps what it can (an AMG its hierarchy). TwoLevel keeps its whole cycle instead, \(A_c\) included, until a rebuild.

The coarse solve is a component like any other, set up on \(A_c\) with a context that says what the coarse dofs are. A callable that builds \(P\) knows that, and returns it with \(P\): for the P1 interpolant, context.ofCoarseNodes(field, isCorner) – the field on its corner nodes, their coordinates – on which DiagonalScaling(TwoLevel(coarseSpace=RigidBodyModesPerAggregate())) works as on any displacement field; for coarse dofs that are no nodes, context.ofCoarseDofs(nCoarse). A fixed \(P\) says nothing about its columns: its coarse dofs are one field of scalar dofs, context.ofCoarseDofs.

\(P\) acts on the matrix the correction gets. The machinery

The adapter, the matrix the tree is set up on, the dumps, and the native cycles behind TwoLevel.

The matrix handed down a composed solver: SystemMatrix.

A component gets its matrix as a SystemMatrix, not as a bare SciPy matrix, for one reason: speed. A diagonal scaling \(\hat A = D A D\) followed by a split into field blocks \(\hat A_{ij}\) would cost a chain of serial SciPy passes over \(A\) – a scaled copy, then a row and column slice per block. Instead, SystemMatrix.scaled() only records \(D\), and SystemMatrix.fieldSplit() forms \(\hat A\) and all its blocks in one threaded native pass (PyAMGCLEquilibratedSystem). The same pass also keeps \(A\) itself as the operator of an outer Krylov solve (SystemMatrix.krylovOperator()), so a field split under a diagonal scaling under a Krylov solver reads \(A\) exactly once per solve.

A leaf that needs the matrix itself (a direct solver, the Schur complement) asks for SystemMatrix.matrix().

The one adapter between a nonlinear solver and a composed solver: ComposedLinearSolver, and the solver script of *linearSolver, type=custom (loadSolverScript()).

The nonlinear solver calls its linear solver as x = solver(A, b) once per Newton iteration. ComposedLinearSolver turns that call into the life cycle of a composed solver: it finds what changed since the last call (a new pattern, a resized system, a jump of the right-hand side that marks a new increment), hands the changed matrix down the tree (update()), and applies the root to \(b\). It is also what reports on the solves: the journal, the warnings, the dumps (solvedumps), and the hot reload of a solver script. Every type of linear solver is a tree behind this adapter (edelweissfe.linsolve.types); a direct solver is a tree of one leaf.

In an input file, a solver script is the custom type:

*linearSolver, name=mySolver, type=custom
script=solver.py

*solver, solver=NIST, name=theSolver
linsolver=mySolver

solver.py builds the tree with plain constructors and binds it to the global linearSolver; it holds only the math, the adapter’s settings (verbosity, dumps, hot reload) are data lines of the block:

linearSolver = LGMRES(DiagonalScaling(...))

Writing the systems of chosen solves to disk, for an offline replay: SolveDumps.

Comparing solver variants by rerunning the simulation is slow and confounded: every run repeats the assembly, and a variant that changes the Newton iterates changes the sequence of matrices being compared. Dumping authentic systems \((A, b)\) once and replaying them offline – through a ComposedLinearSolver with setFieldStructure and the dumped nodeCoordinates and midsideCorners – makes the comparison fast and controlled.

Which solves are dumped is the trigger:

  • "every": every solve (a sequence: whether a symbolic factorization or a preconditioner can be reused across Newton iterations is a question about a sequence, not about one matrix);

  • solve numbers, e.g. {12, 13, 14}: these solves of each solver (counted from 1);

  • "slow": a solve that needs more outer iterations than a threshold, or stops at the iteration cap short of its tolerance. A preconditioner that degrades – a reused hierarchy that no longer fits the Jacobian, a damaged operator AMG cannot handle – typically shows only tens of hours into an analysis, at a solve nobody can name in advance; this trigger decides by the solve’s own outcome.

One snapshot cannot tell an intrinsically hard operator from a solve made slow by its own state (a stale preconditioner): a fresh solver replaying the matrix alone may converge in a fraction of the live iterations. So a dump can also hold the solves that preceded a dumped one (contextSolves), for a replay through one persistent solver in the same order; and every dumped solve records why it was (not) rebuilt.

maxDumps caps the systems written to one directory in a process: a coupled 3D system of a million dofs takes gigabytes on disk. The solvers of all analysis steps that dump to the same directory share that cap.

On disk, in directory: A_<instance>_<solve>.npz (SciPy, uncompressed), b_<instance>_<solve>.npy, schurDofs_<instance>_<solve>.npy (the condensed dofs of a Schur complement, if any), geometry_<instance>_<solve>.npz (the node coordinates of the vector fields, <field>_coordinates, and the midside corners the tree used, <field>_isCorner and <field>_edgeEndpoints, if any) and one line per dumped solve in manifest.jsonl: the field blocks and file names, and the bookkeeping of a Krylov solve in the names of its SolveRecord (iterations, residual, eta, capHit, trueResidualRestarts, rebuildReason, scaledSystem), with patternChanged, newIncrement and previousIterations. <instance> is the ordinal of the solver in the process (one per analysis step).

What the two-level cycles of a vector field (TwoLevel) share: the corner-node two-level cycle (cornernodetwolevelcycle) and the rigid-body coarse level (rigidbodymodestwolevelcycle).

Both are one two-level cycle – fine Chebyshev sweeps on the field’s scaled block, and the coarse correction on the Galerkin coarse operator – that differ in their coarse level and coarse solve: the rigid-body coarse level solves with an AMGCL hierarchy of its own, the corner-node two-level cycle with a component of the composed solver. Both are built and applied in C++: the shared cycle is TwoLevelCycle in amgcl-wrapper.hpp, wrapped as _PyAMGCLTwoLevelCycle in amgcl.pyx. TwoLevelCycle mirrors those bases here: it creates the C++ object, which validates every parameter, and passes the cycle, the fine spectral radius a build estimates, the timings and the report through. A derived class chooses the parameters and builds its coarse level, in its build, from what that coarse level needs.

The rigid-body coarse level of a vector field: the cycle of TwoLevel(coarseSpace=RigidBodyModesPerAggregate()) (TwoLevel).

Why

The near null-space of linear elasticity – the displacements that cost (almost) no strain energy – are the rigid-body modes: three translations and three rotations in 3D, two translations and one rotation in 2D. Smoothed aggregation needs them in its coarse space. An error the Chebyshev smoother leaves alone – its eigenvalues lie below the smoother’s window, which starts at a fraction of the spectral radius by construction – is removed by the coarse-grid correction only as far as the coarse space can represent it on every aggregate.

The block backends of AMG, the default for 2D and 3D vector fields, take the translations alone (AMGCL’s hierarchy on node-wise blocks cannot take more): their coarse space holds displacements that are constant on every aggregate. In a bending-dominated structure – a slender beam, a tunnel lining, a plate – the smooth error is bending, which rotates every aggregate almost as a rigid body. The translations represent it poorly, the smoother does not touch it, and the outer Krylov solve pays with iterations.

What

The rigid-body coarse level keeps the fine level of the block backend – the field’s equilibrated block \(\hat A = D A D\) in node-wise blocks, smoothed by the Chebyshev polynomial of the field’s tree – and builds the first coarse level itself, from all rigid-body modes:

  1. aggregates: AMGCL’s plain aggregation of the nodes, as AMGCL’s own first level on the block backend;

  2. tentative prolongation: the field’s rigid-body modes about its centroid, divided by the equilibration (the near null-space of \(\hat A\) is \(D^{-1}\) times that of \(A\)) – built in Python by rigidBodyNullspace(), the one definition of the modes, and handed to C++ – restricted to every aggregate, zero on the Dirichlet rows (which the cycle solves exactly), and made orthonormal by a QR factorization, as AMGCL’s tentative prolongation does with a near null-space. A mode that depends linearly on the ones before it – a rotation of a single-node aggregate, the rotation about the line through a collinear aggregate, a mode whose components are all constrained – is dropped;

  3. smoothed prolongation: \(P = (I - \omega\, \mathrm{diag}_B(\hat A_F)^{-1} \hat A_F) P_{tent}\), AMGCL’s, with \(\mathrm{diag}_B\) the node-wise \(B \times B\) diagonal blocks of the filtered operator;

  4. Galerkin coarse operator: \(A_c = P^T \hat A P\), 6 coarse dofs per aggregate in 3D (3 in 2D), on which an AMGCL hierarchy continues the field’s tree, with the R factors of the QR factorizations – the coefficients of the rigid-body modes in the coarse basis – as its near null-space.

One application is the two-level cycle the corner-node interpolation (cornernodetwolevelcycle) uses too: restriction of the residual, one V-cycle of the AMGCL hierarchy, prolongation, and the fine Chebyshev sweeps. Everything runs in C++: the steps in amgcl-rigid-body-coarse-level.hpp, the cycle in amgcl-wrapper.hpp (RigidBodyModesTwoLevelCycleT).

When

It is the default of the blockAMG() preset for the 3D displacement field (of any element type), and pays most where the solves would need many outer iterations although the operator is (nearly) elastic: typically a bending-dominated structure. The rigid-body modes are the near null-space of elasticity on the displacement field; a rotation field, or any other vector field, has another, so a solver script gives it the coarse level only by name (OnField("displacement", TwoLevel(coarseSpace=RigidBodyModesPerAggregate())), e.g. for a 2D displacement field). It needs the field’s node coordinates (read from the model), and the field’s tree configures its smoother, its aggregation and the AMGCL hierarchy below it. Its setup costs more than AMGCL’s hierarchy on the translations (the Galerkin product with 6 coarse dofs per aggregate, the larger hierarchy below), so on a model where that converges in a few iterations it gains little. The measurements are in The rigid-body coarse level.

p-multigrid (Galerkin P1 corner-node) preconditioner for one field’s diagonal block: the cycle of TwoLevel(coarseSpace=CornerNodeInterpolation(coarseSolve)) (TwoLevel).

Precondition the quadratic operator through its linear (P1) part: \(\nu\) Chebyshev sweeps on the field’s own (scaled) block, restrict the residual through \(P^T\), solve on the Galerkin-projected \(A_c = P^T A P\) with the coarse component, prolong through \(P\), \(\nu\) more Chebyshev sweeps.

The prolongation interpolates the scaled variables

The block is \(\hat A = D A D\) (a DiagonalScaling above), and a displacement \(u\) of the physical problem is \(\hat u = D^{-1} u\) in its variables. The P1 interpolant acts on \(u\): \(P_{geo}\) keeps a corner node’s displacement and gives a midside node the mean of its two edge-endpoint corners. In the scaled variables the same interpolation is

\[P = D^{-1} P_{geo} D_c: \quad P_{cc} = 1, \qquad P_{ma} = \tfrac{1}{2} \frac{s_a}{s_m}, \quad P_{mb} = \tfrac{1}{2} \frac{s_b}{s_m}\]

for a midside dof \(m\) on the edge \((a, b)\), with \(s\) the diagonal of \(D\) and \(D_c\) its restriction to the corners. The plain weights \(\tfrac{1}{2}, \tfrac{1}{2}\) would interpolate \(\hat u\) as if it were \(u\): a scaled translation \(D^{-1} t\), the smoothest error there is, would be off by the ratios \(s_a / s_m\) at every midside node, and the coarse level could not remove it. With \(P\) the translations are reproduced exactly, and

\[A_c = P^T \hat A P = D_c \, P_{geo}^T A P_{geo} \, D_c\]

is the P1 operator of the physical problem in the corners’ scaled variables: the operator of the corner-node field, scaled by \(D_c\). Without a scaling above (\(D = I\)), \(P = P_{geo}\).

The coarse problem is a field of its own

The coarse solve is a component of the composed solver, set up on \(A_c\) with the context of the corner-node field (ofCoarseNodes(): the same field on the coarse nodes, their coordinates, the scaling \(D_c\)), so that every component works on it unchanged. Its default, DiagonalScaling(AMG()), works on any field; for a 3D displacement field DiagonalScaling(TwoLevel(coarseSpace=RigidBodyModesPerAggregate())) is faster (The corner-node two-level cycle with scaled weights and a composed coarse solve), and the blockamg preset passes it, with the smoother of the corner-node two-level cycle (defaultCornerNodeTwoLevelTree()). Both scale \(A_c\) to a unit diagonal once more: where a midside diagonal is tiny against its corners’, the weights \(s_a / s_m\) are large, \(A_c\) inherits entries of their square, and a Chebyshev smoother on the unscaled \(A_c\) would work with a spectral radius far above that of a unit-diagonal operator.

The cycle runs in C++ (CornerNodeTwoLevelCycleT in edelweissfe/linsolve/amgcl/amgcl-wrapper.hpp, wrapped as PyAMGCLCornerNodeTwoLevelCycle), OpenMP-threaded throughout, and calls the coarse component back once per application.

Dirichlet rows. A field’s diagonal block still carries its Dirichlet identity rows (the Dirichlet elimination runs before the linear solver), and the identity rows of multi-point-constraint slaves, which are treated alike. The fine smoothing and the Galerkin projection act on the free DOFs only, with the Dirichlet DOFs decoupled entirely: the cycle is that of the free submatrix, and a Dirichlet DOF that is only masked after a step still couples into the free DOFs within it. A free midside node whose edge-endpoint corner is Dirichlet-constrained keeps only the surviving weight of its free endpoint – no renormalization (the constrained corner contributes exactly zero to a homogeneous Newton correction, which the dropped weight already encodes). A free midside dof whose both endpoint dofs are constrained (a symmetry plane and a tie on one edge, issue #223) would get an empty row of \(P\) – no coarse correction at all – so its node becomes a coarse node of its own (CornerNodeTwoLevelCycle.coarseNodes), as buildMidsideCorners() makes a node a corner on an AMR edge conflict; it is decided at the build, where the Dirichlet rows are known, not in the topology map. A Dirichlet coarse dof is a zero column of \(P\) and an identity row of \(A_c\): the coarse field keeps its Dirichlet rows, as the fine one does.

The C++ implementation does not extract the free submatrix, it decouples the Dirichlet DOFs exactly inside the full block layout instead: the fine right-hand side and iterate are kept zero on them (a Dirichlet row holds only its diagonal, so every residual and every Chebyshev update stays zero there, whatever the columns hold), and P has no rows for them. That is the free-submatrix cycle up to floating-point summation order, and it is what allows a node-wise 3x3 block storage of the fine operator (fineBlockSize) on partially constrained nodes.
